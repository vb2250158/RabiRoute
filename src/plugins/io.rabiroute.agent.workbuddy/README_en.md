# WorkBuddy（腾讯 AI 办公工作台）

Call public `POST /api/agent/threads` with `agentAdapter: "workbuddy"` and `agentTargetId: "local:workbuddy"` to list tasks, read task metadata, and query native transcripts by exact `threadId`. Use `action: "read"` with `history: { limit: 200 }`, then pass the returned cursor unchanged as `history.cursor`. Pages preserve original events in file order. `coverage` and `warnings` report malformed rows and incomplete trailing records. Queries and explicit-ID delivery work independently, while persona bindings select default routing destinations.

Delivery uses `action: "send"` with the target `threadId`, actual task `cwd`, `prompt`, and a stable `deliveryId`. On Windows, the first scan or delivery discovers the original owner's loopback listener and authenticates with that process's temporary gateway credential. Discovery checks the WorkBuddy process, PID, and creation time. Credentials travel over a private child-process pipe into an in-memory cache. The OS must allow Manager to read that process, including the corresponding access level when WorkBuddy is elevated. This integration remains experimental. Older versions can continue using configured local credentials. CodeBuddy HTTP requests include the required `X-CodeBuddy-Request: 1` header. See the [official HTTP API](https://cloud.tencent.com/document/product/1831/137064).

The 0.1.6 candidate uses `POST /api/v1/sessions/{exact-task-ID}/reply` on the original task process. The host checks its current session ID before native queue admission; a mismatch returns 409 without trying another delivery entry. This call chain does not set or change permission mode; the native task retains tool approval handling. HTTP 200 with `data.delivered: true` acknowledges admission, which may only enqueue work. It does not establish completion or live desktop rendering.

Local screenshots preserve the host's existing textual attachment-reference format, listing absolute paths for the original task's Read tool. Files are checked before sending; prepared delivery saves and rechecks image digests. Paths are not transferred across computers, and a reference does not prove that the image was read.

Use `POST /api/agent/threads` with `action=create`, `agentAdapter=workbuddy`, the project `cwd`, a `title`, the first `prompt`, and a stable `deliveryId`. Register the target workspace in WorkBuddy first. The connector verifies the full path of the native selection before it fills the first message and again when it clicks Send. The request fails if it cannot verify the path. Creation returns the full ID and the native title generated by WorkBuddy. If the API returns `202`, use the original ID and arguments to check the same intent against native history.

As of 0.1.10, creation and continuation requests for unloaded chats can start WorkBuddy minimized when Windows is signed in and the installed app is fully closed. A connected worker is reused. In 0.1.12, continuation waits for WorkBuddy to load the original chat and checks the full chat ID and workspace again before sending. If delivery is uncertain, use the original delivery ID to reconcile the receipt. On Windows, set RABI_WORKBUDDY_RESTART_UNMANAGED=1 in local RabiRoute configuration to let delivery restart a separately opened WorkBuddy under the same Windows user. Delivery resumes in the original chat after the minimized desktop connects. This setting can interrupt running WorkBuddy tasks. Native history and existing creation receipts remain readable while the worker is offline. Scheduled runs without an available receiving session remain readable. Follow up in a regular WorkBuddy chat.

The 0.1.9 Manager plugin reads the existing creation intent and native history directly. Check the result with the same ID and arguments while the desktop connector is offline. Requests with an existing intent only check the original result. The desktop connector owns the first submission.

A connector supporting layout contract v1 reads the plugin's class and component identifiers for each request. The same connection can accept different layouts and still verifies the native workspace before filling or submitting a message. Legacy connectors support the default layout. Adopt the v1 connector through one desktop lifecycle switch. Compatible layout updates then ship in the WorkBuddy plugin alone.

Pass `workbuddyDeliveryMode="steer"` and a dedicated `deliveryId` to `action=send` to guide a local desktop chat. At dispatch, a compatible connector checks the complete conversation ID, workspace, and active state, then invokes WorkBuddy's per-message immediate-send option. WorkBuddy controls insertion and queueing. If admission is unconfirmed, reconcile the original ID against native history. Retain the original IDs of stopped attempts for lookup.

Rename tasks in the WorkBuddy application. Version 0.1.5's generic gateway prefers the original process's primary session and temporarily selects `BypassPermissions`. If the network drops, the server returns 5xx, or the native receipt is missing, retain the original delivery ID and check the original chat.

This package owns the Agent's settings card, discovery, session operations, and delivery implementation. Manager and Gateway use the same native plugin profile. Disabling rejects new work while admitted operations retain their original leases, sessions, and external execution owners. Package metadata declares supported capabilities and maturity.

The manifest declares `entries.web.module: "./web/client.mjs"` directly. The complete Web build generates this file, re-exporting `activate` from the package's independent `/assets/…` module. The publisher pins the card assets to the same Web release; no additional `web.mjs` forwarding file is needed.
