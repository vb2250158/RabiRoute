# Device Agent profile application

English | [简体中文](agent-profile-runtime.md)

Status: source is wired; isolated tests, local AIX test-package builds and parsing checks have been performed. The acceptance matrix tracks the latest integrated regression. Formal installation and device acceptance remain pending; a test package is not an accepted deployed release.

Startup still reads invocation parameters and legacy `rabilink_lingzhu_agent` settings first; legacy records are retained. Only a stored real device credential enables restoration of the independent `rabilink-aiui-agent-profile-v1` cache and retrieval of the device profile. Device profiles override legacy parameters/name settings. Once active, voice renaming directs the user to phone management to avoid competing authorities. Cache scope includes Relay address, device SN and an opaque credential fingerprint, never the raw credential. Ownership changes clear the active profile, pending profile and remote receipt; a busy turn releases its old model when finished. Late reads and acknowledgments are discarded by scope and request generation, preventing an old persona from being confirmed for a new owner.

Startup, first device credential claim, existing manual refresh and the HUD refresh control trigger one GET `/api/rabilink/device/agent-profile`; no polling is added. Without a device credential no request is made, and an application token cannot impersonate device identity. A running turn stages updates without destroying its model. After the turn the profile is saved, and the next turn creates a new model. Storage failure retains the previous model/configuration and shows failure.

Skill guidance uses the bounded schema and `buildAgentSystemInstructions`. Only successful model creation reports the version to `/api/rabilink/device/agent-profile/applied`. Unconfirmed receipts remain explicit; manual refresh reads authoritative state first. Receipt keys are stable by revision/status. Authoritative state is read before and after submission; historical idempotency receipts are not current state. An enabled MCP reference not yet loaded into the current model initially reports `failed/TOOLS_UNAVAILABLE`; initial failure can later become success. Successful application of a revision is permanent: downgrade attempts return `409 PROFILE_ALREADY_APPLIED`. Temporary tool failure is shown locally without consuming new operation receipts. Legacy disagreement between a historical success and current failure remains unconfirmed and asks for a new profile revision from phone management, without automatic migration or random keys.

Applied records one successful application of that revision, not current tool health. It only means page model configuration was created, not a complete tool loop, platform Agent ID binding or real voice-device acceptance. Unpublished tool-result feedback APIs must not be simulated through ordinary prompts.
