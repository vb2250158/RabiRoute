# Glasses as a device Agent

Status: experimental. Source tests cover registration, delivery, claim and receipts. Automatic wake and execution on real glasses have not passed hardware acceptance.

After AIUI opens and creates Rokid's native `LanguageModel`, it registers a name, stable Agent ID and native session ID with the PC recorded as the device's connection owner. A message Route can select `deviceAgent`: the instance ID is the owner's RabiGuid and the Agent ID is the glasses' device binding ID. Renaming does not change identity.

The glasses own inference, generic Rabi API tools, Rokid ASR and TTS. A persona supplies instructions and Skills and chooses the source PC for tools and chat history; it does not restrict API permissions. An authenticated, enabled remote Agent may invoke all public Manager APIs and other PCs within the same application. A Route binding only selects automatic message delivery.

The PC stores one authoritative mailbox and receipt journal. Original `deliveryId` values survive delivery: the same ID and content return the original receipt, while changed content conflicts. The glasses claim and respond using their authenticated device identity, current `ownerEpoch` and server-issued `claimToken`. These fields prevent another client from taking ownership of an executing task. A phone's application credential can manage and proactively deliver messages but cannot impersonate the glasses' executor.

A device session can be the source or target of a formal Agent request. `POST /api/agent/threads` shares the PC's request and reply ledger with other providers, including `responsePolicy=required`, `inReplyToRequestId` and reconciliation of the original receipt. A device needs neither a working directory nor a PC model. Delivery is confirmed only when the glasses claim it with the original session and epoch. Reopening the same session restores its saved epoch. Session and execution caches are separated by normalized Relay URL, credential digest, device ID and physical owner PC; changing servers does not migrate old caches. A new connection or executor never reruns an old delivery in a replacement session.

The persona's source PC, physical device owner and request ledger owner may differ. Glasses can send a formal request directly to another PC in the same application. The receiving PC verifies the actual device owner's session, loaded state and epoch through the existing generic Manager tunnel. Formal replies use the original ledger PC. Before the glasses claim a reply, their PC verifies that ledger's original reservation and transport fingerprint again. The device PC stores transport queues and receipts without copying another PC's business ledger. Persona selection changes neither these identities nor API permissions.

A cross-PC request supplies the model with the actual ledger PC's `targetDeviceId` for its original reply parameters only. Ordinary API defaults and chat-history destinations retain their configured persona PC. A new formal request can explicitly select another PC. An invalid proof, unloaded source or changed PC connection keeps delivery unconfirmed; it never replaces the executor or re-enqueues the operation. An explicit cancellation from the original ledger, with matching delivery identity and fingerprints, marks an unclaimed transport record `result-unknown / ledger_cancelled`. Its evidence survives and later messages can continue. Ordinary rejection, timeout or disconnection is never treated as cancellation.

When the glasses are unloaded, messages remain queued. The phone receives only wake nonces and delivery IDs, sends a custom component command through the existing CXR-L connection and reports its outcome. It receives no execution prompt and creates no replacement model. A submitted command is not proof that AIUI woke: the glasses must register and claim the original message to produce an executor acceptance receipt. A rejected broadcast or timeout preserves the original task and reports the specific failure.

A real device has rejected the two-finger broadcast from an ordinary application. Existing code cannot prove that the system supports programmatic custom-button activation or that every paired physical glasses device matches its binding. Automatic wake still requires hardware acceptance through a supported Rokid entry point. Manually opening AIUI can claim the original message from the same mailbox.

Delivery executes through the existing glasses inference loop and stores results in its original session. ASR can continue during reasoning and TTS; recognized text stops playback only, and final text steers the next reasoning step. Mailbox claims wait for current voice input and steering to finish. Hiding the page, losing the model or switching connections never automatically reruns a task whose outcome is uncertain.

Transport reuses the [generic API client](generic-api-transport_en.md). Unpaired AIUI uses buffered Relay HTTP. A paired phone uses an independent Eye encrypted Manager Tunnel with LAN → P2P → Relay, streaming and WebSocket upgrades. Formal session, claim and response calls preserve that same Eye identity. Protocol source is verified; actual glasses access, HTTPS addressing and transport selection still require hardware acceptance. New PC APIs do not require Relay business adapters.

Developer verification: `src/agentAdapters/deviceAgentOwner.test.ts` exercises real HTTP and PC persistence for original-message delivery; `src/manager/deviceAgentEndpointBridge.test.ts` verifies formal replies through the common delivery factory; `src/manager/deviceAgentPeerEndpoint.test.ts` verifies native session proofs, a single business ledger and actual claims across two independent HTTP Managers; `scripts/Smoke-DeviceAgentPage.mjs` verifies the existing inference loop, voice steering and uncertain outcomes. These tests do not replace real ASR, TTS, button wake or glasses-model acceptance.
