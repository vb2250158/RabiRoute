# Device knowledge write-operation receipts

English | [简体中文](rabilink-knowledge-operation-receipts.md)

This Relay source revision is later than the frozen glasses AIX and PC installer. It is not deployed or included in those packages. Manager remains the knowledge authority; Relay stores only bounded transport receipts returned through the PC tool.

Before dispatch, the existing key/hash intent is persisted with internal owner, target PC, role, tool and opaque credential fingerprint scope. The 128-entry device limit remains fail-closed; no key eviction or lifecycle changes. Results are atomically persisted before responding to the device. Confirmation requires outer and structured 2xx status, no isError, ok=true, uncertain=false, committed, matching key, strong ETag and a nonempty resource ID. Only known receipt fields and business data are retained. Oversized responses above 32 KiB, forged success and 5xx cannot confirm a write. Persistence failure returns uncertain. The failure branch emits `knowledge_receipt_persistence_failed` containing only the server-generated requestId, stage (validate/read/normalize/lookup/write), and an allowlisted error code (EACCES/EPERM/ENOENT/EIO/ENOSPC, otherwise UNKNOWN). Operation keys, bodies, credentials and scope are excluded. Diagnostic logging failure cannot replace the 503 uncertain response or trigger business replay.

`GET /api/rabilink/device/knowledge/operations/:key` requires the actual device credential and returns `{code:0,data:{idempotencyKey,state,receipt?}}`. State is confirmed, failed or unknown; failed requires authoritative not_started. Each read rechecks current ownership, target, role, tool and write permission. It does not require an online PC, call Manager, or touch recent-memory detail. Internal scope and credential fingerprints are never returned; responses disable caching. Revocation and target changes deny access to the old content. Paths are decoded once and keys retain the existing 256-character bound.

Legacy key/hash-only entries and absent keys return unknown, not a claim that execution never started. A restart before the receipt arrives, or worker completion after the request wait expires, may leave unknown permanently; late-result harvesting is not added here. Clients must not repeat POST or change keys to query outcomes, nor treat matching titles as proof of the original operation. Corrupted stored receipts fail validation rather than silently deleting history.

Tests use temporary data, simulated knowledge business logic and real Relay/PC/MCP HTTP. They cover disconnection during business handling followed by GET recovery, confirmed and unknown states across restart, authorization revocation and invalid receipts. Additional tests inject an atomic-write failure into the actual persistence branch (only 503 uncertain is returned) and exercise real HTTP isolation for a second device, owner changes and target changes. The disconnect end-to-end test encountered a five-second persistence timeout during a parallel combined run and passed standalone; a later fixed-source run including safe diagnostics passed 52/52 combined tests and 6/6 dynamic-contract tests, with all 2017 source hashes unchanged. That pass does not explain the previous timeout or establish that its root cause has been eliminated. The end-to-end completion check was subsequently changed from server filesystem notifications to client GET queries using the original key, retaining a five-second total deadline, at most 100 reads, waits of at most 50 ms while unknown, and no POST replay. That fixed-input run passed 52/52 combined and 6/6 dynamic-contract tests with 2017 source hashes unchanged. This improves client recovery acceptance, not the root cause of the historical failure. This revision does not expose glasses write tools, add Manager business logic or modify frozen packages.
