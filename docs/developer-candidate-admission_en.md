# Matching verification for development candidates

Use the existing Host-bound `RABIROUTE_HOT_PATCH_SOURCE_ROOT`, falling back to the existing packageRoot when unset. Place `developer-verification.json` there using the [example](../examples/development-verification.json). No additional environment variable or network configuration endpoint is required. Missing, unreadable or invalid configuration records that development verification is unavailable and preserves formal installation validation; it does not count as a passing development test.

Each `plugins` rule selects a local development plugin by `packageId`, `candidateRoot`, and `verificationConfig`. Relative rule paths resolve against the bound source root. Input/cache roots inside the verification configuration remain relative to that configuration file. A plugin candidate root contains `build-evidence.json` and `packages/<id>/<version>`. `sourcePatches` selects a verification configuration by unique `moduleId`; `web` selects the Web verification configuration. Each rule group is optional. Verification configurations declare matching tests and their input closure without secrets.

Rules match the actual source of the PackageCatalog-verified candidate. Matching candidates run the existing `scripts/verify-plugin-candidate.mjs` from the trusted source root. Missing evidence triggers verification; network-supplied passing flags, paths, or commands cannot replace execution. Unconfigured sources, existing releases, and legitimate out-of-tree packages retain their original installation and Loader contracts.

The whole-build digest differs from a Loader package revision. Admission checks the build digest, actual package contents, and prepared runtime copy separately. Before publication it checks local configurations, the exact candidate object, runtime contents, and application/Manager/plugin generation identities. Changed identities require preparation against the new baseline, preserving original operation IDs and receipts.

The source watcher and local Web import record origin facts in the original candidate store's `developer-provenance` directory, bound to artifact kind, original hash and trusted source root. A Web origin is persisted before exposing a new imported candidate to publication. Manual publication of the same hash and publication after restart read the same origin. HTTP callers reference candidates and cannot supply origin paths. Existing releases without local provenance retain their formal contract. Corrupted provenance rejects only new publication of that hash, leaving the current version and other candidates available. Rebuild or import from the same bound source root to restore the record.

Source evidence uses the original `HotPatchCandidateStore` validation and candidate hash. Web evidence uses the original `verifyWebPatch` manifest, file validation and manifest hash. The verifier freezes these formally built owners and includes their fingerprints with the test inputs; it does not duplicate their schemas. Admission supplies the actual managed candidate path. Tests read candidates through `RABI_CANDIDATE_ROOT`; the original plugin environment name remains compatible. Candidate bytes are checked after testing and before commit.

A failed plugin candidate retains only its previous instance; a new failed candidate is excluded while unrelated candidates continue. Failed source or Web verification preserves the current service and publication state. Failed preparation of a new module allows a corrected registration later. Tests run outside the generation commit queue; the original owner rechecks identity, baseline and evidence before committing. Committed operations return their original receipts. Source rollback and Web previous-version rollback use their confirmed version contracts. Admission owns no publication state. Publication, draining, rollback and receipts remain with the original owner. Shutdown propagates cancellation through CLI IPC to the test runner and waits for exit before temporary cleanup.

Matching verification covers configured plugins, watcher-built source module candidates and locally imported Web candidates. Source bundles prepare every candidate before entering the original transaction; a failed candidate cannot produce a partial commit. The Web candidate in automatic code/Web publication is covered, while the automatic code revision retains its original code-owner validation. A passing Web test does not prove code behavior coverage. Source tests, CLI integration, built-package loading, Manager wiring and installed acceptance require separate evidence. Performance gates still require paired rehearsal and continuous samples.
