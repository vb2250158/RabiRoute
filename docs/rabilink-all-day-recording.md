# RabiLink 全天记录：统一设计、迁移与验收

[English](rabilink-all-day-recording_en.md) | 简体中文

> 状态：**目标设计 / 实施合同，尚未整体验收**。本文定义手机、眼镜和手表整合的目标，不代表当前安装包已经具备全部能力。文档编写不构成代码、构建、部署或真机验收证据。任何阶段只有在对应代码与证据核对后才能更新为已实现；未列出完成证据的项目均待实施或待验证。

## 1. 定位与当前基线

全天记录是一个由用户明确开启的持续信息采集功能：手机作为协调与可靠保存中心，眼镜和手表作为能力不同的输入设备，电脑完成转写与后续处理。音频、音视频、仅健康是模式；运行/暂停是独立状态；转写是同一份记录的后续处理，不再是一套另行开启的录音功能。

“全天”表示持续运行、故障恢复与覆盖可核验的目标，不表示摄像头默认常开、不间断的物理保证、后台权限豁免或可控制厂商所有采集行为。RabiRoute 仍是消息网关和策略调度层，实际理解、回答和动作由目标 Agent/程序负责。

编写时的现有基线：

- 日常四页导航、本地 WAV、视频会话与回放已有入口；新本地录音/录像尚不自动提交转写。
- 持续会话音频有独立可靠 PCM 队列与 PC RabiSpeech 处理链。
- `RabiLocalAudioService`、`RabiLiveRecordingService`、`RabiConversationService` 分别持有运行职责；`CaptureOwnership` 只提供互斥，不等于统一生命周期。
- 本地录音、录像、会话及健康/眼镜状态服务有各自通知路径。会话运行状态、审阅快捷方式和回复共用通知的做法也需要拆分语义。
- 乐奇原生手动推流到手机已有实测记录；自有眼镜组件自动安装/开播及完整眼镜交互仍有未完成验收。
- 健康数据有 Health Connect 与小米 PC ADB Companion 实验链路，不是通用全品牌手表直连。

基线来源：[移动端记录界面](rabilink-mobile-recording-ui.md)、[移动设备消息端](mobile-message-endpoint.md)、[离线录像](rabilink-offline-recording.md)、[健康消息端](rabilink-wearable-health.md)、[Android 工程](../apps/rabi-mobile-android/README.md)。较旧文档的首页/通知描述可能落后于当前界面，应按源码和具体验收记录核对，不反向把目标设计写成现行事实。

## 2. 唯一协调 owner 与分层

手机端只有一个全天记录协调 owner。它持有配置 revision、用户运行意图、实际状态、采集 generation、设备资源租约、恢复策略和常驻通知。类名与文件拆分由实现确定，不能通过多个旧服务共用通知 ID 冒充统一 owner。

```text
全天记录协调 owner（手机）
  ├─ 串行控制与状态事件
  ├─ 手机音频 / 眼镜音频 / 眼镜音视频适配器
  ├─ 健康数据适配器与受控 PC Companion 配置
  ├─ 本地记录索引、可靠分片、缺口与隐私边界
  ├─ 同步/转写任务消费者
  └─ 唯一常驻状态通知
             ↓
  PC RabiSpeech / 健康时间线 / Route / Agent
```

统一产品不等于单一巨型类或深继承树。设备采用组合式能力接口，适配器报告实际数据、连接、错误与停止完成；不得自行恢复麦克风、改变总开关、创建第二份模式真源或抢写常驻状态。

手机 owner 不取代 PC Host/Manager 的进程与业务数据归属。小米 Companion 仍由 PC Host 所属 Manager 插件及 generation process lease 管理，手机只发布受版本约束的采集意图。共享 SDK 只定义稳定契约，不持有产品运行状态。需要访问 Manager 的实现使用动态发现与身份核验，不新增固定地址。

## 3. 配置、模式与运行状态

### 3.1 正交配置

| 维度 | 目标选项 | 合同 |
| --- | --- | --- |
| 模式 | 音频 / 音视频 / 仅健康 | 暂停不属于模式，恢复沿用原选择。 |
| 来源 | 声音设备、视频设备、健康设备 | 保存稳定设备身份及能力，不以显示名称判断归属。 |
| 后续处理 | 仅保存 / 自动转写 / 转写并交给指定人格整理 | 设置不表示相关处理器已在线；仅健康模式不产生虚假转写任务。 |
| 网络 | Wi-Fi 优先 / 允许移动网络 / 暂停同步 | 断网是条件，不是另一种录音功能。 |
| 回退 | 音频自动选源 | 眼镜有音频时优先，断流回到手机；变更来源形成记录边界并显示实际来源。 |
| 保留 | 已确认媒体期限、空间上限、剩余空间水位 | 不静默删除未确认或隔离数据。 |
| 恢复 | 用户同意的启动恢复策略 | 不绕过系统权限或用户明确暂停。 |

建议首版为音频加可选健康、视频手动开启；这只是产品建议，不等于用户已经选择默认或授权自动启用全部传感器。安装/迁移不能自行打开新的采集能力。

### 3.2 状态与命令

用户意图 `running/paused/stopped` 与实际 `starting/recording/degraded/pausing/paused/stopping/stopped/error` 分开。每种输入再有连接状态和最后实际数据时间。仅健康模式不要求音频在线；某个传感器失败不应把仍正常的其他来源显示成完全停止。

所有开始、暂停、恢复、切模式、切设备命令串行处理并具备稳定命令 ID。先持久化意图/边界，再关闭旧 generation 的数据入口、封口保存、等待释放，最后才启动新来源；旧回调不得进入新记录。释放失败保持受限状态，不能先显示新模式采集成功。

- 选择模式不会自行启动；显式开始或既有授权恢复策略才启动。
- 暂停保留模式与设备选择；停止关闭自动恢复意图。
- 用户暂停优先于重连、闹钟、网络恢复、应用重启和后台同步回调。
- 实际覆盖按真实样本/媒体时间区间计算，不用服务存活时长冒充录音或健康连续覆盖。
- UI 由 owner 状态事件更新；重连补一次快照，不用秒级业务轮询。上游没有事件的健康源沿用有界、可停止、低频的已登记例外。

## 4. 页面与唯一常驻通知

目标导航为“记录 / 时间线 / 消息 / 设备”；若过渡期仍使用“首页”，必须通向相同 owner，不新增并列控制面。

- **记录**：总开关、模式、来源、实际覆盖、最近数据时间、本地保存、待同步/待处理、异常与修复入口。音视频/健康分别显示新鲜度。
- **时间线**：按时间关联音频、视频、转写、健康事件、人工标记和缺口；支持筛选、回放与导出。日期是视图分组，不要求零点重启硬件或生成一个全天大文件。
- **消息**：保留人格聊天、附件、普通回复和未读；不再拥有另一套录音开关。转写优先归时间线，不默认每句唤醒 Agent 或刷入聊天。现有 Route 热投递/关键词规则的变化必须显式迁移，不能静默改变已配置行为。
- **设备**：授权、连接、支持能力、最后真实数据、电量、是否参与全天记录和高级诊断；“已授权”不等于“已收到数据”。

常驻通知目标：正常全天记录只有一条，稳定通知 ID 与通道由 owner 维护。显示模式、实际来源、保存/积压或最重要异常；点击始终进入记录页，动作可为暂停/恢复、标记、打开。标记仅添加时间标记，不自动投递 Agent。

普通 Agent 消息使用独立、可清除、按会话归组的通知；点击进入该会话，不覆盖采集状态。系统必要权限提示、紧急故障或显式高级诊断通知不算重复常驻服务。锁屏默认不展示转写、健康数值、密钥或聊天正文。

必须先收敛前台生命周期，再移除旧常驻通知。不得让多个服务通过相同 ID 互相覆盖；不得用麦克风服务类型伪装纯消息保活。运行中的前台服务通知与系统隐私指示不得隐藏。

## 5. 记录真源与可靠处理流水线

### 5.1 来源冻结与数据归属

一份物理声音只采集一次。音视频模式优先消费同一视频音轨进行转写，不再另开手机麦克风重复采集。缺失音轨明确标记，不伪造转写任务；确需独立补充声音须显式配置并保留不同来源。

每个采集区间/分片冻结：稳定记录 ID、采集 generation、本地单调序号、设备 ID/类别、能力与媒体类型、源时间和手机接收时间、时间不确定性、起止范围、字节数、校验和、处理策略版本、目标 PC/Route/人格及隐私区间版本。临时流 ID 不能代替稳定回复设备 ID。视频派生音频保留父媒体 ID、轨道、时间偏移和派生版本。

切换聊天会话不得改变采集目标。改变处理目标只作用于新边界；历史补投/重处理必须是明确操作，保留原归属与独立任务 ID。无目标的仅本地记录不能在以后选择人格时自动全部分享。

手机原始记录/传输分片是本机采集与可靠传输的真源；PC RabiSpeech 拥有成功转写、健康模块拥有健康时间线、人格拥有自身会话与语义判断。移动端统一时间线是关联视图，不复制第二份 Manager/人格业务真源。

### 5.2 保存、同步、处理彼此独立

```text
真实采集 → 有界接收队列 → 单写可靠落盘 → 封口/校验
                                     ↓
                               稳定同步任务
                                     ↓
                           PC 持久接收确认
                                     ↓
                          转写/健康归一化/整理
                                     ↓
                        关联原记录的结果与处理回执
```

- 采集线程不等待网络、ASR 或 Agent。大文件按时长/大小/状态边界分片。
- 复用并保持已有 partial ownership、fsync、原子封口、ACK journal、cleanup tombstone、quarantine 和 gap 的恢复语义，不降级成仅凭“HTTP 成功”删除原文件。
- 接收确认核对序号、chunk ID、字节数和 SHA-256；ACK 丢失后的重放使用稳定幂等键。接收、转写完成、Route 投递分别确认。
- 保存状态、同步状态、转写状态独立展示：例如已保存/待同步、已同步/转写失败、仅保存/未启用转写。不能把“入队”写成“已转写”。
- 非事务处理产生 ambiguous 时保留证据并显式解决，不盲目重放造成重复 ASR 或 Agent 动作。重启扫描只恢复相关持久任务，不全库反复投递。
- 失败项隔离且可见，后续合法项目继续处理；容量不足拒绝新增并记录缺口，不偷偷丢未确认数据。
- 已确认缓存可按用户策略回收；用户明确删除未同步记录必须说明损失，并同时取消相关任务，保留最少删除凭据防止复活。
- TTS 输出不是新输入；抑制回录、实际播放回执和恢复采集仍需设备证据，`delivered` 不等于 `played`。

## 6. 隐私暂停与健康数据不补采

暂停是采集隐私边界，不只是隐藏 UI 或暂停上传。

1. 用户请求暂停时首先持久化排除区间和 generation 边界，停止接收新数据，封口暂停前的有效内容，并停止 Rabi 可控制的麦克风/相机/健康读取。
2. 丢弃或隔离迟到回调及暂停区间样本，不允许在恢复、重连、重启或扩大健康回看窗口时重新导入。
3. 同时按样本发生时间与接收时间判断。健康区间跨越暂停时，仅能在有可信细粒度证据时拆分；否则排除整个重叠样本并说明未知，不凭插值制造缺口外数据。
4. PC Companion 等远端来源也必须执行版本化暂停边界。PC 离线无法确认停止时，手机显示“本机已暂停，远端停止未确认”，不能宣称全链路隐私暂停完成。严格禁止远端继续采集的要求需可过期租约/停止确认等配套实现，验收前不得承诺。
5. 暂停前已经保存的数据默认仍按原授权处理，页面必须明示；提供独立“暂停同步/处理”控制。无法撤回的已提交任务或已分享副本要明确说明，不把关闭按钮描述成远端抹除。
6. 厂商手表可继续独立测量、乐奇原生 App 可继续开播；Rabi 必须说明外部停止步骤。系统时间变更或源时间不可靠时保守排除并标记，不能绕过隐私区间。

原始音视频、健康与转写使用应用私有存储和受控分享；凭据与诊断分离。原始媒体、文字、摘要分别配置保留期限。上传目标、允许接收的人格、删除范围与第三方副本边界必须明确；用户开启全天功能不是默认授权所有人格或外部平台接收全部数据。

## 7. Android 与硬件限制

- 按运行设备/API/target SDK 声明实际前台服务类型、通知、麦克风、相机、蓝牙及健康权限；不能把多个类型无条件一直开启。
- 运行时权限撤销、来电占用、系统强停、开机后台启动限制、厂商省电、健康后台访问限制均可能产生中断。显示恢复操作，不循环违规拉起服务。
- 仅健康或纯消息场景采用合规调度/事件机制；不能因需要常驻通知而虚构麦克风工作。统一 owner 是职责合同，不承诺每种模式都可无限期保持同一 Android 前台执行方式。
- 眼镜原生直播到手机仍需热点/局域网；“不需要互联网”不是“无需任何无线连接”。未验收的自有眼镜自动开播不作为唯一生产路径。
- 小米 ADB Companion 依赖 PC、ADB 与厂商 Provider；Health Connect 是否有样本取决于上游写入和授权。当前模式不等同于 Wear OS 常驻直连已经实现。
- 16 kHz、单声道、16-bit PCM 为 32,000 字节/秒，24 小时约 2.7648 GB（十进制，不含副本与元数据）。视频预算按实际码率测量。配置需考虑容量、耗电、过热与充电条件，未测量不承诺全天音视频续航。

## 8. 无损迁移与旧入口退出

### 阶段 A：控制与通知统一

盘点当前服务、Manifest 注册、设置键、通知 ID、启动/恢复广播、旧 Intent 与后台任务。建立唯一 owner、模式状态与版本迁移。旧服务不得同时自动恢复；停止完成前禁止转移硬件。将普通消息通知与状态分开。

### 阶段 B：记录与处理统一

复用可靠 PCM 队列；新本地音频与视频音轨接入稳定记录/任务合同。新增关联索引读取旧 WAV、视频会话、转写和健康数据，不改写历史归属。对来源缺失的旧数据标记“历史来源未知”，不得按当前人格、邻近时间或相似文件名猜测归属。新本地自动转写尚未完成前继续准确显示仅保存。

### 阶段 C：设备整合与隐私闭环

健康/眼镜适配器接受总意图并报告最后真实数据。PC Companion 配套暂停边界、停止确认与迟到数据过滤必须同步验收；不能只关闭手机按钮。验证模式、回退、数据去重、恢复与覆盖统计。

### 阶段 D：撤掉重复运行路径

迁移需有版本、输入摘要、检查点、结果、可恢复事务和幂等性；保留原文件与未确认队列，失败不清空配置、不启动旧/新双 owner。旧配置多开关冲突时保守保持暂停并提示确认，不自动选择更侵入的模式。

仅有真实外部兼容需要时才保留旧 Intent 的薄重定向；它只能进入唯一 owner，不能启动旧采集实现。每项必须登记兼容调用方、迁移版本、退出条件和验证。无调用方的旧 Activity、Service、Manifest、通知发布路径、设置入口及打包资源应在同次收口删除。历史媒体无需删除；数据兼容与保留旧执行链不是同一回事。

不处理任务范围外的既有修改、删除项或其他应用目录。实际实施报告须逐项列出仍保留的兼容入口；仍有无解释的旧双运行路径时不得标记整合完成。

## 9. 验收矩阵与完成门禁

下表全部为要求，不是已通过结果。

| 范围 | 必须验证的结果 |
| --- | --- |
| 模式与暂停 | 三种模式与运行状态正交；反复/并发命令幂等；恢复不扩大权限；暂停优先。 |
| 唯一 owner | 冷启动、重启、旧 Intent、后台恢复不会启动双麦克风/双采集 owner；释放失败不抢占。 |
| 通知 | 正常运行只有一条常驻状态；普通消息可清除且点击归属稳定；不覆盖录制事实；锁屏脱敏。 |
| 独立离线 | 无账号/无 PC 时允许授权范围内本地采集；断网保存，恢复按原目标补传。 |
| 原子落盘 | 写入、封口、ACK、清理每个崩溃边界可恢复；缺失/损坏隔离可见；不静默丢失。 |
| 音视频 | 真实眼镜首帧、连续流、音轨、切页后台保存与完整解码；视频音轨仅转写一次；无音轨不伪报成功。 |
| 来源与归属 | 切人格/设备/PC/模式不改写历史；来源未知不猜测；稳定设备与临时流区分。 |

## 10. 本轮实施对齐与状态维护

最新源码收口说明：旧独立本地音频、录像和设备状态 service 已移除，`RabiConversationService` 为唯一 owner，视频为普通 controller、音频统一 durable spool、健康为受总许可/窗口控制的 controller。视频停止后才派生音轨，不提供实时视频转写。新记录 ACK 不自动套用传输缓存保留期删除，自动滚动删除尚未实现。PC 仅转写能力/worker 围栏与 captureId 只读关联已接入源码，无能力支持时 deferred。手机仅人工刷新最近 24 小时、最多 200 条、按 processedAt 查询的结果；缺 captureId 不猜测归属，不构成完整历史浏览。健康仅统一采集与状态，完整健康历史仍在 PC。最终源码回归已有 Android 131 项测试、0 失败及 assemble 通过（开发 APK 0.3.23-dev / versionCode 26），根 npm run build 通过。PC 语音相关 Python 测试 66 通过、1 跳过；Manager 语音测试 22 通过；健康 worker 10 通过；Relay 健康与移动审计变异测试 5 通过。上述不替代实际部署、设备及全天验收。

实施协调方已确认以下代码方向正在展开；这是**实施中接口约定**，不是已构建或已验收结论：

- 唯一 owner 沿用并重构 `RabiConversationService`，而不是再创建一个并列常驻服务。视频降为普通 controller；音频统一消费 durable spool 并冻结 record/source/route/policy；健康 controller 受总许可及允许采集窗口约束。
- 新设置模型为 `AllDayRecordingSettings`：`mode=audio|video|health`（UI 对应音频/音视频/仅健康）、`source=mobile|glasses`、`processingPolicy=local_only|transcribe|agent`，以及 `running`、`healthEnabled`、`uploadEnabled`、`autoResume`、`windowStartedAt`。
- `processingPolicy` 默认拟为 `transcribe`，但升级后 `running=false`，不能因此自动开启录音；转写处理默认不等于上传/人格共享授权。仅健康场景不生成音频转写任务。
- `running=false` 表示当前不允许采集，不得作为清空历史暂停区间的理由；`windowStartedAt` 表示当前允许窗口起点，单个当前窗口字段不能替代跨重启、迟到健康样本所需的历史排除区间记录。
- `uploadEnabled` 控制同步许可，`autoResume` 当前仅内部保留 false，无行为的 UI 已移除，开机明确暂停，不宣称自动恢复已实现；前述建议中的 Wi-Fi、独立视频来源和细分运行状态仍需按实际实现逐项确认，不因为字段表存在而声称全部支持。
- PC 端 `transcribe` 仅转写、不自动投递 Agent 的能力与 worker 围栏已接入源码，最终回归与部署验收仍待。在 PC 不支持该策略时应明确报不支持/等待升级，不能静默回退 `agent` 或误报转写闭环完成。

补充实现边界：PC 能力的正/负缓存按端点变化、网络恢复或人工 retry 失效，没有周期性能力查询；离线 PC 升级后需要人工 retry 重新核验，不能承诺自动发现升级。视频已实现持久 binding、停止后的持久入队及死进程身份恢复，但真机验收仍待；健康能力真实 Relay 测试已通过：仅新版 worker 的明确能力可用，旧 worker 不获虚假支持，目标切换返回冲突。`transcribe` 只保存健康记录不投 Agent；旧无绑定或缺少 Route 的记录保留本机，不自动绑定。
