对话消息处理
四类 Agent 协作架构

主人格、秘书和一计划一 Agent 全部保留，新增专职消息处理 Agent。聊天消息先记录，再等待一句话说完并自动形成消息组；ASR 和结构化事件照常直接投递。每张 Agent 卡片只决定是否参与消息处理调度。

谁判断属于哪个计划？ 消息处理 Agent先判断；已有计划交给原计划 Agent，新需求交给秘书 Agent查重维护。
消息处理 Agent 会不会信息过载？ 默认只读短工作状态和本轮新增消息，结束后不保留完整流水。
为什么处理效率更高？ 同组忙碌时只追加队列；不同消息组可以交给其它已开启消息处理模式的 Agent。

04 / DELIVERY

Agent 写回复，RabiRoute 发送

四类 Agent 都只生成结果或回复请求。发送成功只更新状态；失败、需要继续处理或对方又回复时，才把新情况交回原消息组。

蓝色：Agent 负责语义

判断是否需要回复、写回复内容、关联已有计划、识别新需求，以及处理复杂讨论。

  • 主人格、消息处理、秘书和计划共四种 Agent
  • 同一消息组同时只由一个消息处理 Agent 消费
  • 熟悉度匹配只使用卡片已开启消息处理模式的 Agent
  • 计划实施仍由原 taskBinding 对应的计划 Agent 负责

橙色：RabiRoute 负责发送

检查自动发送权限、保存草稿、调用平台适配器、去重、重试并保存发送回执。

  • 回复请求不等于已经发送
  • 只有平台回执证明发送结果
  • 失败恢复不依赖 Agent 记住重试次数
发送结果 RabiRoute 动作 是否启动消息处理 Agent
发送成功，不需要继续处理 把 messageId 和回执写入消息组状态 否，只更新状态
发送成功，但该组又有新消息 回执和新消息一起进入原消息组队列 是，由调度器启动下一轮
自动重试后仍然失败 停止自动重试，保存最终失败原因 需要语义判断时才启动
对方回复已发送的消息 根据 Outbox messageId 找回原消息组 是，形成完整消息包后按队列调度
设计边界：RabiRoute 保证消息有记录、同组单处理者、未提交消息仍在队列、发送有回执、失败能够重新处理；语义不确定时由消息处理 Agent扩大查询、追问或升级给主人格，不能用速度换准确性。
