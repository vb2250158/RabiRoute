# 计划分页读取：缓存、校准与性能边界

[English](plan-page-read-performance_en.md) | [简体中文](plan-page-read-performance.md)

面向维护者。状态：阶段性工程改进，须由正式构建和实际 Manager API 验证后发布；不是十万规模持久索引完成声明。

## 读取链与数据所有权

计划 JSON 仍是权威数据。Manager 进程发布成功写入时同步增加角色级失效版本；分页读任务携带版本，合并在途相同请求时也包含该版本。不同常驻读进程分别消费版本，不能把写入后的请求并入写入前的结果。

读进程先安装目录监听，再创建不可变目录快照。未变化的快照复用展示投影；展示缓存同时核对工作流内容，修改状态名称等配置不会沿用旧展示。原分页过滤、排序、总数、facets、归档视图和 cursor 算法保持原实现，不用实验 keyset 替换公开接口。

## 外部修改与故障

- 精确文件事件与托管版本指定的计划，在回复前重读。读取期间到达的新 dirty 事件也会再消费；连续变化超过有限重试预算时明确失败，不返回已知旧快照。
- 正常监听下，热请求只消费文件事件与托管失效版本，不再每隔 5 秒触发全目录扫描。冷启动、监听失效、未知目录变化和显式刷新仍校准源文件；只列举 active/archive 两个桶，使用最多 16 个并发元数据操作。
- 元数据指纹比较 size、mtime、ctime 和 inode。普通无文件名事件触发完整元数据复核，不一律清空正文；指纹变化才重读对应内容。字段不可用或为零时不信任缓存。监听 error/明确溢出错误、目录替换、版本缺口与显式 `authoritative` 读取仍强制重建正文。冷读在隔离进程中以最多 16 个异步读取循环加载正文并校验前后元数据。
- 未变化正文不重读，签名不变时继续复用不可变快照及展示。这些字段不是任意文件系统上的绝对保证。
- 监听不可用时保守扫描。读取错误失败关闭，下一次请求可以重建；不把失败当成功的空列表。
- 不承诺任意外部写入的线性一致性。监听未报告的外部改动需显式权威重读或重启校准；不是任意延长托管写入的可见性窗口。恢复 mtime 的同尺寸替换在本机隔离测试的校准中可由 ctime/inode 检出，不能外推为所有文件系统的保证。
- 不设后台轮询。监听可用时读取成本不随时间跨过固定阈值而突然全量扫描。

没有采用“每请求只扫 256 个文件后静默返回旧结果”的方案，也没有引入永久后台轮询或第二份业务真源。

## 首屏计数使用交互队列

`GET` 角色知识 `counts` 由现有交互读取池处理，不再排在低优先级 catalog 批任务后。相同角色与失效版本的在途计数合并，写入后的请求不复用旧版本结果；未增加工作进程数或队列上限。计数只读文件元数据，不另建全正文目录。

原五字段完整保留：`activePlans`、`archivedPlans`、`recentMemory`、`consolidatedMemory`、`consolidationRuns`。记忆与整理运行数复用原计数实现；新增异步计划元数据读取的非不存在错误直接失败，不转换为零。

## 有界读进程生命周期

空闲读进程与 IPC 可以解除事件循环引用，但活动请求期限和停止确认期限必须保持引用，直到成功、错误、中止或期限到达。所有结束分支清理定时器。否则独立程序显式 `await run()` / `await stop()` 时可能提前退出；测试不应使用永久保活掩盖此问题。

在项目根目录使用与部署相同的 Node 可执行文件。命令中的 `node` 应解析为该版本；测试只创建系统临时目录，不读取配置中的真实人格。

```powershell
$env:RABI_PLAN_BENCHMARK='1'
$env:RABI_PLAN_FAST='1'
node --import ./scripts/test-manager-runtime-env.mjs --import tsx --test src/rolePlanPageBenchmark.test.ts
Remove-Item Env:RABI_PLAN_BENCHMARK, Env:RABI_PLAN_FAST
```

基准生成 10001 个规范目录，包含冷读、20 次连续分页、三次间隔 5.1 秒的默认 facets 请求、点更与删除。输出保留每个样本、同步/异步 I/O 计数和触发全量校准的原因。它测量读链，不等价于真实 HTTP API；不得只摘取热态 p95 忽略冷读或间隔样本。资源竞争会影响结果，性能负载不要和其它重 I/O 回归并行运行。

## 十万真实 HTTP 失败基线（2026-09-22）

`tests/performance/planApiHundredThousand.test.ts` 接受显式 `RABI_PLAN_API_PACKAGE_ROOT` 构建根，设置 `RABI_PLAN_API_BENCHMARK=1` 和 `RABI_PLAN_API_COUNT=100000` 后运行。先以 1000 条烟测；夹具包含规范状态和历史文件，避免启动迁移修改排序字段。仅启用 core/persona/diagnostics 真实插件，使用临时状态目录、动态 READY 地址和身份复核，不连接业务人格。

0.3.13 候选、Node 24.15.0 的一次十万条测试共约 842 秒（包含约 163 秒数据生成），结果未通过：

- 计划首 8 条、后续分页、筛选与并发组均失败；常见响应为约 30 秒后的 HTTP 500 `Manager read exceeded 30000 ms.`，并发后排另有 45 秒客户端超时。没有成功的计划热态样本。
- knowledge 关键词查询约 149 秒后可用，成功后的四次热请求约 10–16 毫秒；同一已预热索引的全文查询约 23–29 毫秒。首 8 条 ID 与总数通过独立数组 oracle；全文阶段不是独立冷启动。
- 启动迁移最终 `migrated: 0`，测试 Manager 正常关闭、退出码 0。测试不代表已安装运行时或部署验收；进程冷启动不等于清空 OS 缓存。
- 独立复用同一十万目录、绕开 HTTP 请求期限的单次诊断冷读约 119.5 秒：`scanMs` 111.5 秒（其中规范化约 7.4 秒），扫描后的签名、去重、冻结和发布约 8.0 秒。RSS 约 517 MB，仅为该诊断进程，不是完整进程树峰值。`scanMs` 不能解释成纯磁盘耗时。

代码核对确认，分页池超时会终止 Worker 并丢弃其内存缓存，后续请求可能再次冷加载；冷内容读取虽然置于有界异步循环内，正文路径仍使用同步文件操作。上述证据用于后续修复，不是提高超时即可验收的依据。尚需完成冷首屏、完整进程树资源、混合记录类型、写后可见性与游标一致性验收。

### 后续有界异步冷读改进（尚未达标）

将冷读的 stat/read/stat 改为现有最多 16 个循环中的异步操作，保留读前后元数据校验及替换/删除重试。相同目录的独立构建后诊断从约 119.5 秒降至 43.15 秒，紧接的同进程目录缓存命中约 1.54 毫秒；RSS 约 612 MB。该诊断不含 HTTP 与展示分页，冷读仍超过原 30 秒期限，不能声明首屏达标。13 个失效/竞态回归、类型检查和隔离完整构建通过；未部署。基线段落中的同步读取描述指改前版本。

### 可重建检查点与角色级构建（验收中）

分页入口现在由角色级生命周期拥有共享准备任务；调用者中止不终止准备，停止时等待资源退出。检查点位于角色目录的 `.cache/plan-page-catalog.json`，不在 plans 监听树内。它保存规范化记录和源文件指纹，校验格式、角色根、内容校验和及相对路径。恢复时先安装监听，再完整核验源文件元数据、消费已知失效，不能把磁盘投影直接视为 ready 或第二份业务真源。检查点损坏回退到源 JSON；停机期间新增、修改、删除仍以源文件为准。

隔离回归已覆盖未变化正文零重读、停机修改/删除、损坏与越界拒绝，共 16 项通过。Node 24.15.0 的十万条非 HTTP 诊断中，首次构建约 38.46 秒，新进程恢复约 20.09 秒；恢复扫描阶段未发生正文规范化。两次间隔读取仍耗时约 4.61/5.48 秒，说明周期扫描问题尚未解决。诊断进程 RSS 约 889–956 MB，不是进程树峰值。这些数据包含当时的递归冻结实现；后续迭代冻结优化需单独测量，不得沿用这组数字宣称优化生效。

初始化 HTTP 状态、完整端到端重启、长期热态可用率及运行版本验收仍未完成。上述检查点只在冷准备时写入，热请求不全量重写；重启必须重新对照源元数据。

### 事件驱动热读取复测（尚非端到端验收）

移除正常监听下的五秒全量扫描后，16 项回归和隔离完整构建通过。回归将时钟推进一分钟，验证热读取没有同步或异步目录枚举及 stat。十万条非 HTTP 诊断冷读约 31.27 秒；间隔 5.1 秒后读取约 1.14 毫秒，复用同一数组，触发原因为空。RSS 约 891–893 MB，仅为诊断进程。诊断中的 reconciliation 数字是最近一次冷校准的保留值，不是本次热读取耗时。

此前带周期扫描的真实 HTTP 测试仍失败：三次约 45 秒的初始化超时，随后首屏约 272–286 毫秒，搜索约 1.58 秒，一次视图请求约 6.37 秒。取消周期扫描后的 HTTP 复测及初始化响应闭环尚未验收，不将非 HTTP 改善当作完成。

### 显式初始化响应（端到端验收中）

分页 GET 与查询 POST 在共享准备未完成时返回 HTTP 503、`reason: "PLAN_CATALOG_INITIALIZING"` 和 `Retry-After: 2`，不返回伪造的空数据。准备任务独立于单个请求继续运行；就绪后才返回真实分页结果，包括真实空列表。参数错误仍按原合同返回 400。

Web 只对分页读取中的这一精确错误有界串行重试，遵守 `Retry-After`，最多五分钟或 150 次尝试；其它错误不自动重试。页面显示准备中提示，切换人格或隐藏页面会取消当前等待，不终止服务端共享准备。同一查询刷新失败时保留此前数据和游标；切换人格清空旧列表。十二项重试及生命周期单元测试与隔离完整构建已通过；十万 HTTP 二十并发和实际安装版验证尚未完成。

## 十万 SQLite 实验不是生产能力

实验文件位于 `tests/performance/`，不在根 `tsconfig.json` 的 `src/**/*.ts` 编译范围，生产模块不引用它们：

```powershell
node --import tsx --test tests/performance/knowledgeSqlitePrototype.test.ts
```

只有显式设置 `KNOWLEDGE_SQLITE_BENCHMARK=100000` 才生成十万行。Node 22.17.1 / SQLite 3.50.0 的一次隔离试验中，20 个真实读 Worker 执行 480 次查询无错误，但总查询 p95 约 16.98 秒，索引与 WAL 空间约为原文本的 55.81 倍。因此该原型没有获准生产集成，不代表已通过生产十万计划验收，也不能据此否定所有持久索引设计。

后续工作仍包括选择性候选、精确 count/facets 的查询计划与分段耗时优化，以及真实 API 的并发、冷启动与写后读取验收。当前缓存阶段仍有全量元数据校准、点更后的全目录投影和冷内容重建成本。
