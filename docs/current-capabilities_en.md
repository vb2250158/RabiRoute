# Current Capabilities and Maturity

This document describes capabilities that actually exist in the current RabiRoute `0.1.x` working tree. Requirements, design proposals, and external-device ideas are not presented as completed features. The conclusions come from the configuration schema, runtime entry points, Manager APIs, WebGUI, adapter implementations, and current automated tests.

The Message Agent list, task limit, and actual delivery share one weighted order: quoted Agent sends, the original message group, endpoint, conversation, sender, and recent use take priority, with the stable index used only as a tie-breaker. After a limit reduction, unfinished plan-progress notifications, plan/memory callbacks, Agent-to-Agent reply requests, and reminders move to a current task inside the ranked range. After Message Agent mode is disabled, those follow-ups and new chat messages go to the current Route's Primary Persona instead of reopening an old Message Agent task. Completed records retain their original worker for audit.

## Maturity definitions

| Status | Meaning |
| --- | --- |
| `verified` | The repository contains a complete implementation, configuration/diagnostic entry points, and automated contract tests. External platforms may still require accounts, login, or real hardware. |
| `experimental` | The code path and configuration entry point exist, with partial tests or scan diagnostics, but end-to-end compatibility with the external system still requires environment-specific acceptance. |
| `stub` | Only a limited handoff exists, such as opening an app, copying a prompt, or writing a handoff file. It must not be advertised as reliable background delivery. |
| `planned` | Only a proposal or plan exists; the current code does not implement the loop. |
| `historical` | The document records a superseded route, research, or handoff and does not define the current primary path. |

These are the maturity values used by RabiRoute's own scan APIs; they are not production certifications from third-party platforms.

## Current core path

```text
Message Adapter / Manager Entry
  -> JSONL Event Store
  -> RouteDecision
  -> AgentPacket
  -> Agent Adapter
  -> Outbox / Reply
```

RabiRoute owns ingress, rule matching, context packaging, handler delivery, reply routing, and audit. Handlers own answers, execution, tool calls, and their private session state.

## Message inputs

Speech ingress currently stores whole-utterance RMS and peak with timing, source, model, and complete turns once in the host-wide message, then snapshots those facts into each persona's own history/context. The loudness fields describe audio only and do not widen the host identity boundary.

The repository also provides a local voiceprint preflight that composes several TTS voices into one WAV. It verifies per-boundary extraction and clustering inside the composite, but explicit boundaries are not automatic ASR diarization evidence and synthetic output is not eligible for formal real-person calibration.

## Routing and context

- One route can define several message adapters, per-adapter input/output policies, several Agent adapters, a pipeline, a working directory, and persona binding.
- Routing rules live at the root of persona `personaConfig.json`. Several Routes bound to the same persona reuse its rules, speech keywords, and context budgets. Persona-free routes receive default rules, and the role-panel rule is always present.
- Current route kinds are `private`, `group_message`, `direct_at`, `direct_reply`, `indirect_reply`, `heartbeat`, `manual_trigger`, `role_panel_message`, `plan_feedback`, `voice_transcript`, `rabilink`, `wearable_health_alert`, `wecom_message`, `weixin_message`, and `feishu_message`.
- `RouteDecision` only matches rules. `forwarding.ts` iterates active route profiles, writes audit records, and delivers every matched rule.
- `AgentPacket` includes the event, recent bidirectional messages for ordinary endpoints in the current persona/logical endpoint/conversation, role and relative paths, plan/memory/skill indexes, required-read items, log paths, the explicit send API, `sendRequestJson`, and read-only source `replyContext`. Ordinary messages are presented as recent messages, then the current message, then focused discussion and reply evidence. The send template carries the exact Route, channel, and target parameters; source context does not select the destination. For an enabled current Route, `replyContext` also carries a cross-persona capability bound to that Route and persona. When persistent plan-secretary tasks are enabled and bound, it also includes each slot's full ID, name, workspace, and assignment rules. Heartbeat and `plan_feedback` always omit the history section.
- Persistent `协助处理计划` tasks are plan-management secretaries, not business-execution owners. A Route has a separate checkbox to enable or pause them. Pausing retains the exact task bindings but stops injecting secretary slots and automatic secretary-model selection. Manager owns one `codexPlanAssistantModel` for every secretary on the Route, defaulting to `gpt-5.6-terra`; the task array no longer stores separate model choices. A model explicitly requested for one delivery still takes precedence. Each plan stores its responsible Secretary in a separate `secretaryBinding`, while `taskBinding` identifies only the independent business task. WebGUI guidance/approval goes to both the business task and responsible Secretary; business-task completion, ordinary progress, and state changes go to the Secretary first and no longer wake the Primary Persona by default. Every guidance or approval turn must write its result with stable ID `response-<feedbackId>`. On startup, Manager scans `pending/failed` records, recognizes that linked result first, and then reads the bound task by the original `feedbackId`. Accepted deliveries receive only the missing receipt, active tasks wait, and confirmed-missing deliveries are replayed once during that Manager process. If Desktop accepted a turn but the IPC response timed out, Manager briefly polls readback; a still-active delivery remains `pending` instead of being marked failed or replayed. The Secretary consumes results, updates plans and memory, and continues the business task. It escalates only decisions, approvals, authorization, missing user input, cross-plan conflicts, complete closure, or safety-reviewed outbound communication. Neither a Secretary nor its temporary control-plane child Agents may modify business files; investigation, implementation, and validation stay in the business task. Real Desktop multi-task acceptance remains pending, so the feature is still experimental.
- Codex Desktop delivery is sharded by the complete `threadId + workspace`: different tasks may enter Desktop IPC concurrently, while deliveries to the same task remain ordered so two requests cannot both try to start a new turn. Manager reads and updates one plan through its canonical plan-ID file, falling back to a directory scan only for legacy non-canonical filenames; separate secretaries no longer reread every plan and every approval record for a single-plan operation.
- Message-group processing is experimental. With `messageProcessingAgents.codex.enabled`, chat messages automatically write raw and persona conversation records before settling into recoverable groups; there is no per-endpoint off switch. ASR/voice transcripts and structured events continue direct delivery. Dispatch ranks the total score: when a group message quotes an Agent-sent platform message, RabiRoute traces the send session by endpoint, platform message ID, and Route and gives the matching complete session ID in the current pool the largest single preference; prior-group, endpoint, conversation, and speaker familiarity still contribute. Optional `messageProcessingAgents.codex.maxAgents` limits the pool to `1–32` tasks. At the limit, an existing task is reused even while active; a value of `1` keeps `协助处理消息1`. Lowering the limit removes excess tasks from the Route pool state without deleting Desktop tasks. Historical records retain their original worker, while later plan-progress notifications and plan/memory callback reminders resolve against the current pool and no longer target removed workers. An older receipt without sender data, no matching pool task, or a lookup failure does not block the message and only removes this extra preference. Only tasks that Codex currently reports as `idle` participate in ordinary idle reuse; an existing `notLoaded` task is opened through the normal Desktop-owner path and reused. If Desktop is offline or current status cannot be read, the group remains queued for retry instead of creating from stale local state. Without a configured limit, expansion is allowed only while Desktop is online and every registered task is explicitly active or reserved by the current allocation. Tasks use stable persona-prefixed `协助处理消息` titles, add one-based numbering when multiple workers exist, and migrate old titles by renaming the same task ID without changing its owner. `agents.json` stores task identity and initialization metadata only, familiarity recovery is stored in `routing-affinity.json`, and active/idle/notLoaded always comes from current Codex state. Message Agent turns use `gpt-5.6-luna` / `medium`. Fragments arriving during delivery remain queued as same-group supplements instead of being removed with the preceding batch. Explicit DMs, direct mentions, and direct replies now default to a visible acknowledgement: even when no plan is created or implementation is deferred, the Agent states what it understood, who acts next, and what will resume the work. “No plan work” is not treated as “no reply.” Ambient group messages remain selective and trigger a response only when they assign action, correct direction, report risk, or continue an Agent commitment, preventing reply spam. Recovery validates persisted state again: derivable runtime fields receive safe defaults, while groups missing required message identity, conversation, or content fields do not enter scheduling. **Message Agent mode**, **Plan assistant tasks**, and **Hook management** are capability-gated handler extensions and are currently supported only by Codex; other Agent cards do not show them and non-Codex configuration does not retain them. Automated tests cover recovery, deduplication, offline waiting, `notLoaded` reuse, concurrent supplements, quoted-send-session weighting, task limits, and HTTP delivery; live group/DM and four-Agent acceptance remain pending, so this is not verified capability.
- With Codex Message Agent mode enabled, Manager persists a separate message-delivery requirement state and shows it on the Route configuration page. Explicit mentions, direct replies, private messages, and plan-progress notifications are required items; ordinary group discussion remains an Agent decision. The board reads the same Manager-owned state and shows the current stage, worker task, handoff target, no-reply reason, Outbox receipt, failure, and overdue duration. Delivery presents broader recent bidirectional messages first and the current source message next, with the complete reply chain and nearest five-minute discussion fragment adjacent to that current message; QQ images are sent as local image inputs that Codex Desktop can inspect. An outcome must record the reviewed source-message IDs, reply-chain IDs, and an observation for every attachment. If an image is unavailable, the Agent may retry or hand off but cannot guess from text and reply. Before a reply, the Agent must also read the latest bounded bidirectional context; approval is bound to the context version, complete sending session, destination, and payload. A new conversation item, a prior Agent reply, a changed requirement state, or a changed send request fails closed. Primary Persona and other Agents cannot bypass requirement tracking when replying to the same source message. A send completes only when `status=sent`, the channel matches the source endpoint, and platforms such as QQ return a real platform identifier; TTS success cannot close a QQ requirement. A structured handoff may associate the source conversation with a `planId`; later status, current-step, next-action, wait, or step-progress changes made through the canonical plan writer create notification requirements automatically. Relevant unit tests and the backend build cover source-evidence and pre-send context review. The board WebGUI was unchanged in this work, while live platform delivery and long-running acceptance remain pending.
- Persona `recentMessageLimits` configures ordinary endpoint budgets from `0` to `200`, with a schema default of `12`; zero disables only injection. Heartbeat is always treated as `0`. `conversation/current.jsonl` has no entry-count cap, time-based archives use `archive/<n>~<m>.jsonl`, and automatic context never reads archives.
- A Route may store several Agent configurations, but matched ordinary messages are delivered only to the Primary Agent selected by `primaryAgentAdapter`. When Codex is primary, delivery goes directly to the Desktop owner through `steer/start`. A primary failure does not switch to another Agent. Heartbeat may separately skip while busy, and speech may separately use hot/keyword delivery.
- Delivery replay is implemented. Real delivery writes `delivery-replay-ledger.jsonl`, and attempts or stored messages can re-enter the delivery path.
- Persona-route dry runs and `AgentPacket` previews remain planned; the current WebGUI has no side-effect-free preview API.

Handler creation now uses the Cordis runtime: all five built-in Agent Adapters register as independent Fibers in one catalog, while type parsing, Gateway configuration enums, Manager scan metadata, and Quick Setup input read one manifest. The compatibility entry and existing delivery paths remain unchanged. Automated tests cover disposal of one Fiber and the root Context. Manager publishes the unified plugin catalog through `/api/plugins/catalog`; WebGUI generates controlled navigation from it and reacts to catalog changes, while Desktop reads the same catalog for host-pre-registered menus, status, settings, hotkeys, and theme entries. Third-party Vue components, scripts, styles, and command handlers are not open yet.

Command, file, network, permission, and tool approval in the target Desktop task remains separate from RabiRoute's external-message Outbox policies.

## Outbox and explicit sends

`POST /api/agent/send` is the only Agent outbound endpoint. It requires a stable `deliveryId`, the calling Agent's `sender.agentType + sender.sessionId`, exact `routeId`, `channel`, channel-specific `params`, and `payload`; legacy `/api/agent/replies` is removed. It returns `sent`, `draft`, `blocked`, or `failed`. Completed sends can be queried by `deliveryId` or traced by channel and `sentMessageId`.

| Output | Current behavior |
| --- | --- |
| QQ / NapCat | Requires an explicit group/private target and supports text/image/voice/file payloads. Local group files must pass `allowedFileRoots` and use `upload_group_file`. Every group send must include `params.replyToMessageId`: a real ID creates a quoted reply, an empty string explicitly selects no quote, and omission returns an actionable error. A quoted image message also requires ordered `replyImageDescriptions`; after a successful send, a same-name `.md` beside every image records the description and Agent-session mapping. |
| WeCom | Requires an explicit `params.chatId` and sends through the SDK under adapter policy. |
| Personal Weixin | Supports text or allowlisted local-file replies only to a source session that has already supplied a context token. Arbitrary proactive contacts and dedicated image, voice, and video output types are not implemented. |
| Feishu | Supports text replies only to the source `chat_id`, gated by application credentials, event-subscription enablement, and adapter output policy. It does not fall back to the generic Webhook adapter. |
| FenneNote | Retired; reply/playback forwarding remains only for legacy Routes, not as a new output design. |
| RabiLink | Route policy gates sends; every request must name device IDs or device kinds, and non-proactive sends also require `sourceMessageId`. Proactive downlink does not require a fabricated source task. |
| Role panel | Appends directly to the role timeline and may include attachment descriptors. |

The Plans page now records feedback associated with a `planId/stepId` and can notify the Agent through the independent `plan_feedback` system event. This is scoped to Agent-maintained plans, never advances a plan directly, and is not the generic persistent Outbox Action Queue. `draft` remains an Outbox result and audit state, not a completed unified approval product.

## Manager and WebGUI

- The Manager serves RibiWebGUI and HTTP APIs at `http://127.0.0.1:8790/` by default and owns route configuration, child-process lifecycle, scans, logs, and global settings.
- Manager runs large voice-history reads in dedicated worker threads: at most two execute concurrently, at most eight wait, and each has a 30-second deadline. Capacity and deadline failures return explicit 503/504 responses instead of making the main HTTP thread unresponsive. Time-bounded voice queries use the archive index to exclude non-overlapping files before reading their contents. Simultaneous summary-only requests for the same range share one scan. `GET /meta` exposes active, queued, and configured limits under `readWorkers`.
- Full Route diagnostics read only bounded JSONL tails and reuse the same file result within one response. When persona conflict history has no snapshot yet, the endpoint returns 202 immediately and starts a rate-limited catalog task in a separate single-worker pool. That pool waits for at most one task, allows up to five minutes, does not consume a voice-read slot, and avoids full-speed directory traversal competing with page reads. `GET /meta.catalogWorkers` exposes its state. Manager also limits header receipt to 10 seconds, request receipt to 30 seconds, idle keep-alive to 5 seconds, and one connection to 100 requests; `GET /meta.httpLimits` exposes these values.
- The Console can explicitly enable LAN WebGUI access and generate or rotate a dedicated key in `data/Config.json.webguiLan`. After Manager restarts, listening changes from loopback to the LAN; a page opened locally through `localhost/127.0.0.1` then redirects to the preferred LAN IP while preserving its current Route and page. Non-local Manager API, SSE, and private-resource requests must carry `webgui_token` or the dedicated request header; loading the static shell alone grants no data access. The switch and key can be managed only from the Manager PC itself through loopback or one of its own LAN addresses; other devices remain denied. Changing the sidebar **Current Route** redirects `#/routes/<Route-config-name>/overview` or `knowledge`, and the Console can copy the corresponding complete link.
- After signing in to RabiLink Relay management, `https://<relay>/manage/<account>/<RabiGUID>/` exposes the selected PC's complete WebGUI control plane. Ordinary APIs, images, attachments, audio, downloads, and video ranges cross the application-token-authenticated PC worker; Manager SSE uses a dedicated live event channel. The management cookie, RabiLink application token, and LAN `webgui_token` remain three separate boundaries.
- Current WebGUI areas are Console, Message Adapters, Persona Configuration, Plans & Memory, Speech Service, Model Management, Log Diagnostics, and User Guide. Model Management is host-scoped and does not follow the selected Route. Quick Setup selects inputs, handlers, and a persona.
- The first WebGUI read now returns complete editable Route configuration without logs, message files, or full persona bodies. Console, Message Adapters, and Log Diagnostics request the heavier runtime diagnostics only when needed. Persona Configuration shows at most 420 characters of plain-text summary; **View full document** opens a separate Markdown reader. Both pages read the selected `persona.md` through the controlled persona-file endpoint instead of embedding every persona body in the initial `/gateways` response.
- A **Multi-PC persona sync** button in the Persona settings header opens a dedicated workspace. After a PC is selected, a read-only preview shows Changed Files before the user selects **Pull and synchronize**. The conflict catalog can contain a large history, so it is still read only after the user selects **Check conflicts**; file events refresh that catalog only after the page has explicitly loaded it once.
- **Identity positioning** is split into **Recognized identities** and **Unrecognized identities**. The first groups confirmed QQ, WeChat, voiceprint, and other endpoint accounts by person; the second groups accounts whose owner is still unknown by endpoint type and never merges them by nickname. A recognized person uses the whole card as its entry point. One workspace then maintains basic details, endpoint accounts, speaking habits, and relations without a three-dot dropdown or separate long-term and short-term relation types. A voiceprint can be explicitly linked to one confirmed identity and unlinked from that identity workspace if the association was wrong. The voice section does not scan the last 24 hours of history on initial entry. The read starts only when the user selects **Refresh classification** or begins **Mark next segment**; later recording and relationship events refresh it only after that section has been activated.
- Plans & Memory separates content into four tabs: **Current Plans**, **Recent Memory**, **Consolidated Memory**, and **Archived**. Recent Memory contains only unconsolidated records, Consolidated Memory contains stable recallable outputs, and Archived combines archived plans with source memories marked by `consolidatedAt`. The page first reads eight Manager-sorted plan summaries or 24 memory items. Before mounting the initial plan cards, it fetches complete details for all eight cards in parallel, so the first screen does not show a plan-detail loading state. While visible, it completes the selected plan category automatically in pages of up to 250 summaries and the visible memory category in pages of up to 100 items, without requiring scroll; the loaded and total counts remain visible. Later plan pages omit the status and tag facets already returned on the first page, and Manager uses compact JSON for API responses. A hidden tab pauses the background work; visibility triggers a refresh and continuation. Each page yields one rendering frame instead of waiting for body hydration. The body mounts a bounded forward window from the selected directory target and initially mounts eight plan cards and 24 memory cards. Scrolling down mounts later plans in bounded batches; scrolling up restores earlier plans in bounded batches and preserves the current card's viewport position. A directory jump gives the target detail request highest priority and is accepted against a one-second interaction budget in the current Manager and LAN environment. Other body text, steps, approvals, and attachment metadata hydrate only for cards genuinely near the viewport; each observer turn promotes the nearest ten cards with at most ten concurrent requests. A full-content search requests the remaining details only when needed. Image/video attachments use light loading/failure placeholders and low-priority lazy loading so large knowledge sets do not block the first screen.
- Plan-list sorting supports status, update time, importance, and urgency. Update time uses a timestamp; Manager projects status, importance, and urgency to integer levels before sorting. Importance prefers `importance`, converting legacy `priority` once at the read boundary. Urgency prefers `urgency`, with legacy plans optionally deriving a compatibility level from `dueAt`. Labels and palettes are mapped separately for every level, and each directory row shows exactly one trailing label for the active sort mode.
- Recent Memory cards show recorded time separately from the last true recall hit and safely render Markdown text/images. Manager arms a one-shot task for the earliest 72-hour deadline, then freezes the trigger time and 24-hour candidate ceiling and delivers the run automatically; late execution does not append later boundary crossings. WebGUI shows the separate countdown, least-active memory, candidate count, and card markers only during the final 24 hours. Recent source records from a completed consolidation are not candidates again, while generated consolidated memories remain recallable.
- Console manages the Rabi instance name/GUID, global RabiLink Relay connection, route/role directories, and route lifecycle.
- Message Adapters includes NapCat multi-instance management, Remote Agent discovery/connection, external-adapter diagnostics, Agent scans, Primary Agent selection, pipelines, and working-directory configuration.
- Persona manages persona content, route variables, rules, route kinds, regex, schedules, and templates. The proposed dry-run preview is not implemented.
- Log Diagnostics displays connection state, the Codex delivery channel, recent logs, and manual triggers. Delivery replay has a Manager API and ledger, but the current page has no replay control.
- The top bar supports runtime switching between Simplified Chinese and English. Locale state has one owner and is stored in browser `localStorage` under `rabiroute:webgui:locale`, with `<html lang>` kept in sync. It is a UI preference and is not written to Route, role, or Manager configuration.
- English mode translates only registered interface copy and dynamic status text. Route/persona IDs, rule names, templates, regexes, task names, paths, tokens, logs, and runtime data remain unchanged. User Guide renders the manually maintained Chinese and English Markdown under `docs/user-guide/` instead of creating a third page-content source.
- Manager also exposes Agent thread bridge, Role Knowledge, Remote Agent, multi-Rabi, NapCat management, and RabiLink remote-WebGUI HTTP/SSE proxy APIs.

## Role knowledge and runtime data

- Plans, recent memory, consolidated memory, consolidation runs, and skill indexes all have Manager APIs and file sources of truth. New memories use Markdown while legacy JSON remains compatible.
- AgentPacket `message_delivery` and Codex session, prompt, PreToolUse, and PostToolUse events all enter `RabiContextManager`; it is the only production role-knowledge snapshot call site. Entry events use full context, while reasoning hooks inject only newly matched deltas for the turn.
- The Codex handler now has Hook management. Task-entry context fires on `SessionStart` / `UserPromptSubmit`, reasoning-time refresh fires on `PreToolUse` / `PostToolUse`, and plan-task completion notification fires on `Stop` after the bound execution task outputs its final answer. A Route can also enable **Require the RabiAgent message delivery API**, which denies Primary Persona, Plan Agent, Plan Secretary, and Message Agent attempts to bypass Rabi for other persistent tasks during `PreToolUse`. All four default to on; switches control Manager response only and do not change plugin registration.
- Every non-empty RabiRoute handler delivery carries `messageSource` and starts with `[消息源]`, then `[消息内容]`; the Agent adapter interface itself accepts only a structured envelope. Source types are message endpoint, Agent, plan, and system, each with its own required name and complete-ID fields. `contextBlocks` follow message content and `controlBlocks` follow context; neither may nest message-envelope headers. Legacy `[投递源]` wrappers, nested envelopes, Agent response wrappers, and replay records have migration paths, while an unrecoverable old replay is labeled `历史投递记录`. Required Agent responses are experimental: Agent-to-Agent delivery must choose `responsePolicy=required|none`; non-empty `create` and `send` requests with `type=agent` require the Agent endpoint, session name, complete session ID, and matching `sourceThreadId`, and Manager replaces stale names with the actual owner name. Manager persists required requests, and a formal response carries the request ID, result, and next action. If the target turn ends without that response, Manager reminds the exact task five minutes later. A formal return from a Message Agent handoff restores the publishing worker to continued processing. Automated tests cover the state machine, APIs, Hook denial and Stop handling, plugin output, and WebGUI build; sustained five-minute reminders across real Desktop tasks still need end-to-end acceptance.
- Experimental plan-task completion reminders are implemented. A plan binds an exact independent business task through `taskBinding`; omitting `completionHook` defaults it to enabled, while `completionHook.enabled=false` disables one plan. With Plan Secretary enabled, the `Stop` Hook sends the official final answer directly to the responsible `secretaryBinding`, without writing the Primary Persona role-panel timeline. The Secretary updates plan/memory and continues the original business task, escalating only decisions or complete closure. A missing usable Secretary falls back to the same persona's Primary task. Secretary rotation or plan pause never clears the business binding. Conflicts fail closed. Code, HTTP, plugin, and mock delivery tests exist, but real Desktop acceptance is still pending.
- Memory hits refresh `viewedAt` through one policy; the same item revision is not refreshed twice in one turn. Manager automatically creates and delivers a run at the earliest 72-hour deadline; manual triggers and API requests remain available. Submitting the result marks the inputs and writes consolidated memory. A Codex Route may send automatic and manual triggers to a dedicated `<Primary Persona task name> 记忆整理` Desktop task, defaulting to `gpt-5.6-terra`, without Primary-Persona fallback on failure.
- The Codex plugin only forwards lifecycle events and injects Manager output. It owns no binding, trigger policy, or knowledge copy. The internal `preview` policy is side-effect-free, but no WebGUI preview surface exists yet.
- Runtime records are primarily JSONL: messages, adapter logs, AgentPacket, Outbox, heartbeat, manual trigger, role panel, RabiLink conversation, role-scoped wearable health timelines, and delivery replay.
- Runtime `data/`, logs, tokens, real account IDs, real group IDs, and Cookies must not enter the repository.
- Multi-PC persona synchronization is experimental: PCs under one RabiLink application token discover peers, prefer the dedicated LAN data plane, and fall back to restricted Relay transit. JSONL uses union merge; ordinary files use common-base fast-forward, known-base one-sided deletions propagate, and delete-versus-edit or two-sided changes retain evidence under `data/persona-sync/conflicts/`. The same persona, path, peer, remote hash, deletion state, and base hash now map directly to one canonical evidence hash, so automatic reconciliation never traverses the legacy conflict directory merely to deduplicate a conflict; historical copies are grouped asynchronously only after the user explicitly checks conflicts. A rebuildable manifest index performs one startup reconciliation and then rehashes changed paths from filesystem events; hosts without reliable events reconcile once before a query. `PersonaSyncAutoReconciler` treats local file changes, peer availability, and Relay `ready` as wake-up signals, persists pending scope, and performs one manifest catch-up. Offline targets wait for events, while temporary online failures use bounded backoff rather than fixed business polling. A local Agent or the persona page can inspect evidence and keep local, accept remote/deletion, or submit merged content. Resolution verifies local hashes, retains an audit record, and publishes back only while both endpoints still match the evidence. Conflict control plus index/automatic-state diagnostics are never exposed through LAN or Relay. Compatibility voice-endpoint classification events carry `supersedes` lineage, so concurrent decisions retain conflicting heads until a later persona PUT explicitly converges them; `semanticConflicts` returns in the same sync response. `scripts/test-rabi-persona-sync.mjs` still performs one explicit physical-PC synchronization and writes sanitized evidence.

## Capabilities that must not be advertised as complete

- A generic Action Queue / approval center and automatic retry queue.
- Side-effect-free WebGUI preview for persona routing, RouteDecision, and AgentPacket.
- Reliable background Marvis session injection.
- A production-complete loop for every RabiLink phone, glasses, watch, and Xiaomi Health route. The repository contains implementations, probes, acceptance material, and designs, but their maturity is not the same as the core router.
- Future APIs, UI, and hardware paths described only in design, research, or handoff documents.
