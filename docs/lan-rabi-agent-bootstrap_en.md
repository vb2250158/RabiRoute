# Remote Agent setup and updates

Connector 0.2.11 fixes upgrades retaining a launcher generated by the retired release. After verifying its pointer and identity and crossing the commit fence, the successor atomically refreshes the launcher from its own code before reporting success. Failure is recovered by the stable owner without replaying tasks. Preparation and connection preserve the original launcher.

Windows connector 0.2.10 fixes status and recovery commands failing once status history exceeds 512 characters. Owner handshakes remain separately checked; authenticated receipts support the full bounded history and chunked Unicode text, so growing status history no longer breaks query or recovery commands.

Connector 0.2.8 locates npm in the current Windows, macOS/Linux or Homebrew Node installation and supplies the running Node directory to installer PATH. Installation explicitly includes optional dependencies. Before acknowledging readiness, POSIX candidates start and exit a real terminal; missing dependencies are repaired first, and failure retains the current version. If an older Mac connector reports missing npm, retain its identity and credential, install the signed candidate's dependencies with npm from that Node installation, then hand off.

The onboarding prompt inspects existing installations before choosing first enrollment, reuse, offline recovery, upgrade or credential repair. Existing nodes retain their configuration, identity, valid credential, Agents, tasks and workspaces. Timeouts and offline status trigger connection diagnosis. Disk files, the current-release pointer and the running process are checked separately; identical version numbers still require content-digest verification. If new files are installed while an old process remains active, switch only the connector and retain existing artifacts and upload receipts.

Upgrades prefer the connector's signed update and IPC handoff. Manual migration first backs up the private configuration, release pointer, launcher, Hook and startup entries, drains accepted tasks and stops the original connector before switching to the verified release. Every launch specifies the same explicit `--config`. After the new connection and relevant read-only capability checks pass, remove this instance's superseded releases, duplicate scripts and obsolete login entries, leaving one active startup entry. Before deletion, verify installation-root containment, absence of process/pointer/Hook/startup references and ownership by this configuration. Retain configuration, credentials, tasks, logs, workspaces, uploaded files and private recovery backups. Failed verification restores the old program entrypoints without deleting the old release; successfully repaired credentials must not be replaced with invalid old values. Report ownership conflicts separately.

Connector 0.2.6 makes the copied connection prompt sufficient for enrollment and credential repair; no additional Agent approval or controlling Agent is required. Valid saved credentials are reused. If credentials are missing or rejected, the fresh ticket repairs the original node while preserving backend settings, workspaces and explicit disables. Before exchange, the client saves a private `config.json.enrollment.json` recovery record containing its node identity and a random recovery secret, never the ticket. A lost response is resolved by authenticating the same credential. After interruption, rerun the same `--bootstrap`; an exact completed exchange can also be recovered after Manager restart. Deleted nodes and replaced credentials cannot be restored with a spent ticket. Keep the recovery file private until success, when it is removed. Only an expired or unavailable ticket requires copying a fresh prompt.

> Status: experimental integration. Connector 0.2.6 removes session registration and per-Agent grants while retaining the default-enabled instance switch. Source tests, the combined build, host deployment and each physical remote client require separate acceptance.

Remote Agents connect as execution targets only: select an enrolled instance and Agent in the Agent section. The old message-endpoint menu, quick setup choice, and password-based device scanning panel are removed. The legacy `remoteAgent` message-endpoint key remains only for saved configuration compatibility; remove it after instance/Agent bindings migrate and old task receipts are archived. Do not use it for new connections.

## Remote CMD and PowerShell

The client executes computer operations without a running Codex/DSH backend. The host computer's Rabi service owns persistent management without a separate controlling Agent. Ordinary authenticated Agents can query plans, recent and consolidated memory, and skills; the corresponding Rabi service remains their data owner. See [remote computer clients](remote-computer-client_en.md).

Connector 0.2.4 adds POSIX interactive terminals for Mac/Linux, advertising installed Zsh/Bash/sh shells. Keep optional dependencies when installing node-pty. Mac uses a current-user LaunchAgent and may need Xcode Command Line Tools for native compilation. Windows window queries and screenshots have not been ported to Mac. Native Mac terminals and Desktop IPC still need an online device for acceptance.

Windows connector 0.2.2 provides both shells by default. In **RabiLink → Remote Agents → online computer → Remote terminal**, create, query, attach to and exit sessions. Closing the window retains sessions; exiting a terminal ends its descendants. Transport disconnection and main-program exit end all terminals. Existing connection authentication is reused, and commands run as the remote connector user. See [remote terminals](../apps/rabi-agent/README_en.md#remote-terminals-022-experimental) for operation and capacity boundaries.


## Three user steps

Windows connector `0.2.1` provides a local tray: double-click for status/logs, or use the menu to control the connector, open host management and change login startup. One main program owns the connector and tray children and releases them on exit; Codex/DSH remain independent. After upgrading an older node, exit its original main program normally and launch once through the existing launcher; enrollment and task bindings remain. Local isolated tray validation is covered; real two-computer upgrades and login startup are pending. See [Windows tray](../apps/rabi-agent/README_en.md#windows-tray-021-experimental).

1. Open **RabiLink → Remote Agent** (远端智能体 in Chinese) (`#/rabilink?tab=agents`; the old `#/lan-agents` redirects here) and select **Copy setup prompt**. One click issues and copies the complete setup instructions together with a single-use ticket, valid for 30 minutes after issuance and invalid immediately after one successful exchange. No manual WebGUI key is needed. The prompt uses the current Manager LAN address and pinned release public-key fingerprint. A loopback page selects a current LAN address. Enable LAN access first. Copy a new prompt after expiry or a Manager restart.
2. Select Windows, Mac (macOS) or Linux before copying its setup prompt. The target Agent inspects existing installations first; only a first installation creates an empty Agent catalog and registers current-user startup. Existing installations retain their bindings. Verify Node.js 22.13+ and CPU architecture, and verify signatures, content digests and files when downloading is needed. Installation adds no Agent association or default task and requires no running Codex/DSH host. This replaces the old download-before-inspection prompt flow.
3. Once online, use computer APIs directly. For Agent messages, explicitly choose the actual type and full session ID, then select **RemoteAgent(<IP address>)** under **Message adapters → Add AGENT**. Computer identity remains the stable instanceId.

Local and remote computers use a two-level **instance → Agent** view. The local instance appears automatically. Connector 0.2.9 reports the OS hostname, so remote cards default to **computer name (IP address)**. Existing unnamed nodes acquire it after upgrading and reconnecting; older nodes without a reported hostname temporarily show their stable instance ID. Use the pencil to save a single-line alias of up to 80 characters, including while offline. Manual aliases take precedence; clearing an alias restores the hostname. The connector owns the hostname and the current Manager owns the alias, which reconnecting cannot overwrite. Terminals, Route choices and recent tasks share this display rule. Names do not change identity or permissions. In the API, `name` remains the manual alias and `hostname` is the reported computer name; `expectedName` remains empty when no alias is set.

Developer API: `PUT /api/lan-agent/instances/:instanceId/name` accepts an authenticated enabled connection and `{ "name": "Build computer", "expectedName": "" }`. Read the current name first, retain the expected value, and read back after success. Conflicts return 409; no additional browser login is required.

The shared instance editor provides names, enablement, workspace, task names and IDs, model, reasoning effort, explicit environment scans, opening tasks and Hook installation. Hook policies remain in the current Manager's persona automation settings.

The prompt contains a short-lived enrollment ticket, not the shared WebGUI administrator Token. Paste it only into a private task on the target computer; never put it in a repository, group chat, logs, screenshots or command history. Clipboard fallback supports LAN HTTP pages; HTTP does not encrypt transport, so use it only on a trusted network.

Remote connector 0.2.6 authenticates the entire computer with its enrollment credential. Enable Agent is one instance-wide switch, enabled by default. An enabled instance can use all public host APIs, including renaming, plans, memory, Skills, files and tasks, without browser login, a primary Agent, session registration, binding or per-feature grants. Every Agent call supplies its actual type and complete session ID; directories and session lists are discovery, not permissions.

Use `PUT /api/lan-agent/instances/:instanceId/enabled` with `{enabled, expectedEnabled}` booleans. Read the current value first and read it back after saving. The retired per-Agent `/authorization` endpoint no longer exists. Switching the instance off and on fences old in-flight requests.

Exact `GET /meta` checks Manager identity for diagnostics. Business calls accept live healthy or degraded instances; the requested operation checks its own dependencies. `requiredReady=false` does not block unrelated operations.

Manager and connector runtime verification are separate. Two-computer acceptance requires a connected remote node running the matching connector; historical deployment records below do not establish that a later change is live.

### Connected node with an empty resource catalog

A `200` response with `data: []` from `GET /api/lan-agent/resources` does not mean authorization was denied; authorization failures return `401/403`. Manager reads public resources from the current installation's `packageRoot/skills` and allowlisted `packageRoot/docs`, not the writable `stateRoot`. The old wiring incorrectly returned an empty catalog when an installed deployment separated these roots. After fixing or upgrading the host Manager, use the existing node credential to list resources and read `docs/rabi-agent-interfaces.md`; do not re-enroll, repeatedly grant access, or copy documents into the state directory as a workaround. Verify connectivity, resource readability and macOS login startup separately.


### Older nodes must enroll again

An old configuration without `nodeCredential` cannot reuse `lanLinkToken` as a node credential. Enroll with a new ticket while preserving `nodeId`, Agents, task bindings and permitted workspaces. Reconnecting with an existing independent credential does not exchange another ticket. The new source implements a safety migration before any HTTP/WS listener opens: when old `lan-agent-tasks.json` exists without a completion marker, it rotates the WebGUI Token even if that registry is empty, then writes the completion marker only after success. A migration failure aborts startup. Old browser remote links become invalid; obtain new links locally and update trusted management clients. Confirm revocation or rotation separately for exposed shared keys outside this detection scope. **An unrotated shared key may still bypass node grants through administrator access; disabling an Agent grant does not revoke that key.** A successful deployment and healthy Host do not establish older-node migration acceptance. Re-enrollment and invalidation of old keys still require per-node verification; do not describe all existing installations as already automatically secured. Connector 0.2.5 retains the same private recovery proof and checks uncertain exchanges automatically; rerun bootstrap without an additional Manager approval.



## Ownership and execution

| Object | Owner | Behavior and acceptance |
| --- | --- | --- |
| Nodes, IP, connections and task states | Manager node registry | Both HTTP management and WebSocket connections require explicit authentication; offline delivery fails. |
| Route binding | Route `agentAdapters`, `remoteAgentTargets`, and `primaryAgentTarget` | Local providers and remote targets are stored separately. Remote entries reference `instanceId + agentId` without copying credentials or task configuration. The primary selects a specific target, not just a Codex/DSH provider. Gateway receives its endpoint and credential from the current Manager generation. |
| Task, model, tools and permissions | Existing remote Codex/DSH host | Each Agent retains its task binding. No fallback Runtime or host startup modification. The host remains independent when Manager stops. |
| Background connection | Current-user Rabi Agent | Owns outbound connection, downloads, verification, login startup and updates. |
| Message path | Route → Agent adapter → Manager registry → remote worker → bound task | Codex uses Desktop IPC; DSH uses local `session.prompt` with `mode=queue`. Each host has one execution path. |

An unavailable Codex owner fails without `codex app-server`. An unavailable DSH endpoint or binding fails without switching to Codex. A busy Codex task rejects new work rather than overwriting its task association. Accepted duplicate tasks are not submitted again.

Online means the worker is connected. Task records distinguish delivery, acknowledgement, progress, completion and failure. DSH currently reports queue acceptance; read its actual reply in the bound session. Codex completion comes from Desktop broadcasts; read replies in the corresponding task. Local image paths are not sent directly to another computer. Full plan-assistant and message-processing-pool parity and remote persona-file synchronization still need verification; do not claim that all advanced local features have migrated.

## Installation and releases

| Platform | Private directory |
| --- | --- |
| Windows | `%LOCALAPPDATA%/RabiAgent/` |
| macOS | `~/Library/Application Support/RabiAgent/` |
| Linux | `~/.local/share/RabiAgent/` |

WebGUI owns the single prompt template; this document does not duplicate it. The prompt contains the full Manager URL, single-use ticket and pinned SHA-256 public-key fingerprint. The ticket permits release downloads and is consumed by a successful enrollment. The resulting independent `nodeCredential` is stored only in the node's private configuration; Manager stores only the secret hash and grants. Login startup entries contain no credentials. Verify the Ed25519 manifest signature and every file's SHA-256 and size. Reject escaping paths and cross-origin downloads. Preserve Manager's private signing key across upgrades; rotation requires trusted redistribution of the fingerprint.

Process variables: `RABI_MANAGER_URL`, `RABI_AGENT_BOOTSTRAP_TICKET`, `RABI_NODE_ID`, `RABI_AGENT_DEFAULT_CWD`, `RABI_AGENT_ALLOWED_CWDS`, `RABI_AGENT_RELEASE_PUBLIC_KEY_SHA256`. Codex uses `RABI_AGENT_TYPE=codex-desktop` and `RABI_AGENT_CODEX_THREAD_ID`; DSH uses `RABI_AGENT_TYPE=dsh`, `RABI_AGENT_DSH_URL`, `RABI_AGENT_DSH_SESSION_ID`. The remote Agent discovers and privately stores these values without asking the user to type IDs.

`node rabi-agent.mjs --bootstrap` stays running; launch it hidden and detached from the installation terminal. Refresh the node page after setup. Manager advertises the current content digest in authenticated connection events. Updated connectors automatically update unless private configuration explicitly sets `autoUpdate=false`, including changed content with the same version. Downloads still verify the pinned key, signature and every file hash. Address changes trigger bounded discovery using the enrolled stable `guid`, with automatic identity verification; Agents do not manually recheck identity, rebind, redeem tickets or request another token. Never scan or guess ports. Report the failed discovery stage rather than declaring Manager offline.

Updates identify releases by the SHA-256 digest of signed `manifestPayload` JSON. Downloads use immutable digest-named directories and recheck release identity and every file hash before reuse. Updates are single-flight. The candidate reports prepared over IPC without connecting or executing work. The old owner waits up to 30 seconds for accepted work to drain; timeout retains the old release without cancelling or resending work. Only after the old connection closes does the candidate activate and reload current bindings. Connection readiness precedes the atomic `current-release` commit; execution and updated notifications are released only after commit. Failure first confirms candidate exit, then restores the previous pointer, launcher and Hook bytes and reconnects; an unconfirmed candidate never races a restored owner. Shims read the current pointer on invocation. Candidates without IPC handoff support fail safely rather than reverting to connection takeover. These are source and isolated-fixture contracts; real two-computer upgrade acceptance remains separate.

The local trusted publication owner can call `LanAgentReleaseStore.importRelease(frozenAgentRoot)` to copy an already frozen and reviewed directory into an immutable signed snapshot. HTTP never accepts a publication directory or arbitrary code. `assignRelease(nodeId, releaseDigest, expectedReleaseDigest)` persists a stable node's version selection with a digest compare-and-set; `releaseDigest=null` returns it to the common release. Candidates retain the original signing identity. Failed imports and CAS conflicts leave selections unchanged. Data lives under the private state root at `data/lan-agent-releases/`, without changing the common Agent root.

The local trusted publication owner can also freeze the common release explicitly. Construct `LanAgentReleaseStore` with the immutable package `agentRoot` that currently supplies the common release, then call `publishCommonRelease(expectedReleaseDigest)`. Before the first freeze, read the current digest from the original owner still publishing that package. To advance later, construct the owner with the new immutable package and supply the previously read common digest. Under the shared selection lock, the method compares the current digest, verifies the original signing identity and all current and candidate assets, then atomically stores the full manifest, digest and immutable package root in `data/lan-agent-releases/common.json`. Original download URLs, signed payload and digest remain unchanged; no `?release` is appended and no node is notified or reset. Replacing or restarting the Manager does not advance this record.

Reads prefer a node-specific archive, then the explicit common selection, then the original packaged default only when no common record exists. Damaged common metadata or a signature/digest mismatch fails closed instead of adopting the new Manager package. Asset reads check each file's size and SHA-256. Missing or invalid current/candidate assets, CAS conflicts and atomic replacement failures do not commit a new common selection. HTTP accepts no source path for common publication; no environment variable, permission switch or feature allowlist is added.

An old immutable package referenced by the common selection, or an archive referenced by a node selection, remains an external compatibility resource rather than disposable build cache. The local owner method above is the only common-release advancement path; node-specific releases retain `assignRelease`. Remove old packages or archives only after confirming that no common or node selection references them and all original download/update transactions have completed. Do not edit or delete selection records to bypass failures.

The existing `POST /api/lan-agent/nodes/:nodeId/update` accepts `releaseDigest` and the required `expectedReleaseDigest` when `version` is omitted. It selects an already imported signed snapshot for that connected node, then sends the original update notification; conflicts return 409. Signed manifests, reconnect notifications and asset reads without a snapshot parameter select by the trusted credential's nodeId. Unknown and unassigned nodes, ordinary application connections and bootstrap retain the common release. The signed download URL's `release` parameter pins an immutable snapshot across assignment changes. Selection is not an API permission: other authenticated connections retain all public APIs. If selection commits but notification fails, the response marks `uncertain`; inspect that node's manifest before retrying rather than assuming its pointer stayed unchanged. Evidence covers source and isolated HTTP/WS fixtures only. The original maintenance owner must backport the contract for older installations; real signing, assignment and upgrade require separate acceptance.

Older connectors without content digests, IPC handoff or dynamic discovery cannot be declared migrated merely because a new manifest exists. A necessary first installation updates only the connector and stable launcher, retaining the original `nodeCredential`, nodeId, Agent, session and workspace bindings. Valid credentials do not require new ticket redemption, node deletion or rebinding. Existing DSH processes may cache helpers; replacing files does not establish hot loading. Use the original host's managed reload and verify actual release digests and Hook behavior.

Startup covers the connector **after the current user logs in**, not prelogin Codex/DSH Desktop availability. Windows uses a hidden VBS login entry. macOS uses current-user launchd `RunAtLoad`, failure keepalive and 30-second throttling. Linux prefers user systemd `Restart=on-failure`, with an explicit desktop-login fallback when unavailable; no linger or system service is enabled. The stable launcher owns one worker, uses bounded exponential backoff after abnormal exit and rereads the current pointer. Successful exit or `--stop` does not revive it. IPC transfers the committed update candidate to the same launcher; old-worker exit never starts another worker. Temporary processes, Windows VBS and three-platform configuration fixtures cover this contract, not real remote reboot or native macOS/Linux login acceptance.

### Lifecycle and retired entrypoints

- Manager's node registry owns remote enabled state and catalog projections; remote private configuration owns credentials, workspaces and host bindings. Catalogs, Skills and Routes are not additional API grants. Host exclusively owns local Manager lifecycle; the remote stable launcher exclusively owns connector-worker lifecycle. Neither creates a fallback business Runtime.
- Launcher ownership and endpoint writes use separate kernel listeners as mutexes, released on crash. Windows uses named pipes derived from canonical config-path hashes; Unix uses one hash-derived loopback listener. Collisions are explicit busy failures, never scanning or takeover. These local mutex/control endpoints are not Manager discovery addresses. Old `launcher-owner.json`, `.recovery`, pathname sockets and `.endpoint-lock` no longer determine ownership or receive writes; stale PID evidence does not authorize deleting them. Stop old connectors before migration, rather than mixing writer versions.
- Endpoint persistence merges only verified address/identity fields and CAS-checks the original node, credential and endpoint fields, preserving concurrently updated Agents, workspaces and `autoUpdate`. Launcher diagnostics are not lock authority; stop uses the same kernel owner.
- Skill ZIP download and generic HTTP calls share `/meta` unwrapping and identity contracts. Shared Hooks follow the committed pointer. Re-running an obsolete bootstrap does not roll back a valid installed pointer. A candidate that fails final commit verification exits nonzero for recovery by the original launcher, instead of retaining fake IPC liveness or reporting updated.
- This closes the inspected active call chains, not every remote historical OS startup entry. Windows temporary-process/configuration fixtures, mocked macOS/Linux activation and actual login acceptance remain separate evidence.

## Instance ownership and management

The local instance ID is persisted in private `agent-instance-id.json`; remote instances retain their private nodeId. Single-task settings no longer synthesize agentId=default. Existing catalog identities remain intact, and new Agents receive UUIDs. Every delivery explicitly supplies its provider and full session ID without rebinding a configured task first; see [remote targets and list queries](rabi-agent-interfaces_en.md#explicit-remote-agent-targets-and-list-queries). Each executing computer owns its configuration. Manager keeps a catalog projection, while local Agents keep their existing route configuration as the source of truth, with the existing concurrent-version guard on saves.

Computer operations reuse the enrollment credential. Scan, task and Hook RPCs retain request IDs and connection ownership; each invocation supplies its provider and full session ID without Agent registration. Read original receipts after uncertain results.

Message processing and memory consolidation retain the original tasks and workspaces. Creating or listing a session does not enroll it in an allowlist. Calls carry the actual computer, type and full ID; offline or unavailable hosts return their original errors.

Installed Manager reads connector assets, the shared management runtime and Hook packages from its immutable release, while signing keys remain in private data. Reconnecting preserves instance identity, the Agent catalog and permitted workspaces. Disabled local task bindings remain visible and can be enabled again. A Route can retain local Codex and multiple remote Codex targets, with independent cards, removal, and selection. Adding a remote target neither replaces the local card nor changes the primary. Removing the primary requires an explicit new selection; an offline remote target never falls back to local.

Legacy `agentInstanceBindings[provider]` is migrated only at the configuration read boundary: local configuration fields are retained and remote bindings become independent targets. An existing remote primary continues to select the same instance and Agent. Saving removes the legacy field so deleted targets cannot reappear. Migration does not create sessions or change node grants; local cards without a bound session still require configuration.

## Calling APIs and skills from a remote task

On a remote computer, prefer the installed connector command supplied by the Hook and its `--api` entry. The examples show arguments, not a requirement to find another source checkout. Local `RabiRouteHost.exe` discovery instructions apply only on the Manager computer; absence of Host on the remote computer does not mean Manager is offline. The connector automatically discovers the current address by stable Manager GUID, verifies `/meta`, and reconnects; the client owns ports and runtime generations, without a second Runtime or credentials in command arguments:

```bash
node rabi-agent.mjs --api GET /api/lan-agent/capabilities --agent-type codex --id "<FULL_SESSION_ID>"
node rabi-agent.mjs --api GET /api/lan-agent/resources --agent-type codex --id "<FULL_SESSION_ID>"
node rabi-agent.mjs --api GET "/api/lan-agent/resources/read?id=docs%2Frabi-agent-interfaces.md" --agent-type codex --id "<FULL_SESSION_ID>"
```

Supply `--agent-type codex --id "<FULL_SESSION_ID>"` on every call. No saved Agent/session registration is needed. The CLI reads the computer credential privately and checks the current Manager identity before and after requests. Preserve strong ETags, stable idempotency keys and authoritative readback after uncertain results.

- `capabilities` describes current operations and parameters; it is not an instance permission allowlist. Existing public operations remain callable even when not listed.
- `resources` lists only public skills and explicitly published documents. `resources/read?id=...` permits those documents, `SKILL.md` and controlled text directly referenced by that same skill. It does not provide arbitrary `file` access, path traversal, link escapes, private data or host files. Reading a script does not authorize executing it.
- The catalog advertises only published files and references that can actually be read; arbitrary Markdown links do not grant access. Public contracts cover interfaces, plans and memory, context injection, and remote setup, with corresponding English documents. Use the actual IDs returned by `resources`. Discovery endpoints are `/api/lan-agent/capabilities` and `/api/lan-agent/resources`, not `/api/agent/capabilities` or `/api/agent/resources`.
- Persona Skills use `GET /api/roles/:roleId/skills` (summaries) and `GET /api/roles/:roleId/skills/:skillId` (detail); the `/roles/...` aliases have the same boundary. Requests authenticated with a node credential and enabled Agent identity can read each persona's effective Skill directory like local Agents, without an additional persona Route binding or per-Skill grant. Route bindings are not Skill-read authorization sources; the shared request authentication still rechecks Agent enablement, node revocation, computer credential incarnation and this invocation’s explicit source. Local management retains its existing authentication. This does not merge host-global or private Skill directories, or publish private Skills, credentials or synchronization configuration through public `resources`.
- Both persona Skill listing and detail use the bounded interactive reader pool, not the bulk catalog queue. Disconnects cancel reads; busy queues, task deadlines and unconfirmed worker termination return `503`, not a successful empty list. A missing Skill within an authorized persona returns `404`; a genuinely empty directory returns `200` with an empty list. Verify these persona authorization and scheduling changes against the deployed version: source tests do not mean all running nodes are updated.
- Fetch the latest skills and contracts currently published by Manager on demand, then read references available in that catalog. Do not keep a copied skill tree as another authority. Plans, memories and message-processing state remain Manager-owned; do not create a second remote business-state store.
- Agents authenticated at the shared ingress and still enabled have local-equivalent public management authority, without a remote-only operation subset, Route-primary prerequisite or additional WebGUI token. The operation catalog is discovery, not a public management authorization allowlist. Raw-path, encoding and query-credential checks, shared object permissions, Action Gate, file roots, confirmation, version and idempotency conditions remain. Read-only mode and generation fences apply equally. Agent enablement does not replace authentication for Host-private lifecycle, device resource keys/owners or Peer receive protocols. Unauthenticated browsers retain the existing local/WebGUI-token boundary. Secondary handlers are still undergoing implementation and verification; this is the source implementation contract, not proof of parity acceptance for every API or running node.
- JSON bodies use the local `readJsonBody` default and each endpoint's explicit limit, without the additional remote-only 1 MiB cap or any new shared cap. Source-identity validation, upload limits and existing business-handler checks remain. QQ message reads and model-directory settings use the shared authenticated principal, never source metadata or a forged Agent header. Recheck original authorization before awaited disclosure and settings writes, with no loopback fallback after revocation. This round is not deployed; complete queue and streaming fences remain in progress.
- Revocation checks retain the request's original computer credential, instance-switch incarnation and explicit source; disabling and re-enabling or re-enrolling cannot restore an old request. Storage mutations recheck across asynchronous reads, queue admission and dispatch, then use a dispatch-specific IPC admission handshake before the worker reads receipts, recovers transactions or accesses domain data. An allow is irreversible admission for that complete operation: later revocation does not roll back admitted commits or recovery, and there is no guarantee of zero publication after revocation returns. Denial or interruption after dispatch conservatively leaves commit state unknown because the same idempotency key may already have historical writes; perform authoritative readback, never blind retries. This admission mechanism is undergoing source-level development and validation; deployment and two-machine acceptance are not complete.
Channel sends reuse the authenticated instance connection. The sender supplies its actual type and full session ID; Route-primary and saved session bindings do not add permission gates. Preserve the original deliveryId, exact target, channel parameters and both Manager/channel receipts.
- Cross-Agent delivery supplies source and target types, full IDs and computer locations, retaining the original delivery and receipt. Do not infer sessions from old Agent registrations. Hooks use `/api/codex-hook/context` with this invocation’s actual type and full ID.

The Windows release process will copy public `skills/` through a controlled Git-tracked file selection, excluding private or untracked workspace content. ZIP acceptance has not been run for this packaging chain; do not claim that the installed package already contains a complete usable skill catalog.

### Open a WebSocket from discovery

The source generic client adds `createManagerClient(...).openOperation(operationId, options)`, sharing address discovery, identity checks and catalog caching with HTTP. Developers explicitly supply `onMessage`; the protocol owner sends native first messages in `onOpen`. JSON and binary frames follow contract schemas/capacities. After requesting closure, await `channel.closed` outside callbacks for cleanup. The actual connector also opens its native channel through discovery, removing its fixed connection path while retaining native authenticate/hello, node/task identity and its existing reconnect owner.

This requires a Manager publishing executable WebSocket contracts and a signed connector release containing the new modules. Missing contracts produce compatibility errors without guessing paths or enrolling another node. CLI adds `--operation ID --websocket --output FILE [--frames-stdin]` for streaming JSONL frames. Normal remote EOF drains accepted frames; output commits without overwrite after original Manager identity verification. See [WebSocket CLI](rabi-agent-interfaces_en.md#lan-agent-websocket-connection-contract-source-connected-installed-acceptance-pending) for options and the [connection contract](rabi-agent-interfaces_en.md#lan-agent-websocket-connection-contract-source-connected-installed-acceptance-pending) for SDK semantics. Installed deployment and real two-computer acceptance remain incomplete.

### Download one Skill and its support files

When the Skill body is readable but `scripts/` or `references/` files are missing locally, download that Skill's complete directory. Do not copy the whole persona or guess host filesystem paths. An Agent configured for the persona reuses its existing node credential and persona permission. This endpoint does not execute scripts.

The installed launcher uses the current immutable release directory as its working directory; `./` does not refer to your shell or project directory. Explicitly choose an existing parent directory on this computer outside the Rabi Agent installation and pass an absolute file path to `--output`; the final file must not exist. Use the Bash example below only if you have chosen and confirmed that `$HOME/Downloads` exists and is outside the installation; otherwise substitute your chosen existing directory. Do not create directories automatically. The shell expands `$HOME` to an absolute path.

```bash
node rabi-agent.mjs --api GET "/api/roles/<roleId>/skills/<skillId>/download" --agent-type codex --id "<FULL_SESSION_ID>" --output "$HOME/Downloads/selected-skill.zip"
```

Use the installed connector path supplied by the Hook. Manager and remote connector versions require separate acceptance: a new Manager does not prove that the Mac already has a CLI supporting `--output`. Upgrade old connectors through the installation/signed-update flow above, then verify the Hook and CLI option; do not install a second updater. The HTTP endpoint can also be used independently by an authenticated binary client. The destination parent must exist and existing files are not overwritten. The client validates ZIP length, SHA-256 and Manager identity before/after transfer before reporting success; it never extracts or executes content. The ZIP root is `<skillId>/`, containing all regular support files in that Skill directory. A flat Markdown Skill contains only `<skillId>/SKILL.md`. Download another Skill separately; external references are not followed. Links, escapes, unsafe names and exceeded limits fail the entire package rather than silently omitting scripts. Consult the deployed [download contract, limits and errors](rabi-agent-interfaces_en.md#download-one-complete-skill-folder).

Downloading `.ps1` on macOS does not prove that `pwsh` exists, paths are suitable or execution is authorized. This covers registered Rabi Agent downloads from their configured Manager; public RabiLink large-binary forwarding and real cross-machine acceptance are separate.

## Upload a file and send it to a QQ group

> Upload integration, the full build and deployment were verified locally in `0.3.4-4b5d30118b40`. Tests used real HTTP and simulated NapCat without sending files to a real group. Real two-computer group-file delivery remains unverified.

Requires an independent node credential and a primary Agent approved by the controlling Manager. Upload only transfers a file to Manager; it never automatically sends to a group. See the [upload example in the interface contract](./rabi-agent-interfaces_en.md#uploading-from-a-remote-agent-before-sending-a-group-file-experimental-contract) for the complete send JSON:

```bash
node rabi-agent.mjs --upload <file> --agent-type codex --id "<FULL_SESSION_ID>" --upload-id <UUID>
node rabi-agent.mjs --api GET /api/agent/uploads/<UUID> --agent-type codex --id "<FULL_SESSION_ID>"
node rabi-agent.mjs --api POST /api/agent/send --agent-type codex --id "<FULL_SESSION_ID>" --body-stdin
```

`--upload-id` is a required stable UUID saved beforehand, never generated automatically. Upload uses `PUT /api/agent/uploads/<UUID>`, `application/octet-stream`, the same UUID as `Idempotency-Key`, `x-rabiroute-file-name` containing a URI-encoded basename, and `x-rabiroute-content-sha256` containing the content digest. GET on the same path returns `{code:0,data:{id,fileName,size,sha256,expiresAt}}`, with ISO expiry and no local path. Defaults are 2 GiB per file (2048 MiB, the hard maximum), 4 GiB total, at most 100 files, and a 24-hour TTL. HTTP uploads have a total concurrency limit of 4 across owners. After timeout, 503, a generation change or an uncertain receipt, rediscover and verify Manager, then GET the original UUID; never automatically retry or change IDs.

Large uploads use binary streaming, streamed disk writes and incremental SHA-256 verification with a 30-minute deadline, not whole-file JSON or memory buffers. In RabiLink → Configuration, save `agentUploads.maxFileMiB` (integer `1..2048`, default `2048`), persisted in `data/Config.json` and effective after Manager restarts. Authenticated remote Agents that are not explicitly disabled can likewise modify it through `PATCH /api/rabi/identity` under shared parameter, strong ETag and idempotency contracts, without another feature grant.

A controlled 734 MiB (769654784-byte) file passed size/SHA-256 integration verification through the real client, loopback Manager, managed disk and simulated NapCat. Generation and sink reads used 64 KiB chunks, with test guards rejecting Buffer allocations/concatenations above 8 MiB. The large case requires `RABI_TEST_LARGE_UPLOAD=1` and automatically cleans temporary files. **Actual QQ-platform acceptance of this file size remains unverified**; check NapCat/QQ limits and group permissions. Legacy connectors require the new bootstrap (preserving their node credential), and hosts caching an old Hook must reload. Updating Manager alone does not add large-file support to an old client.

Sending still uses `/api/agent/send` with a stable `deliveryId`, `sender`, exact `routeId`, `channel=napcat`, and `params.target=group`, `groupId`, `instanceId`, and `replyToMessageId`. The reply ID must be a concrete message ID or an empty string. The file portion of the standard-input JSON is `payload:{type:'file',fileId:<upload-data.id>,fileSha256:<upload-data.sha256>,text?}`. `fileId` is mutually exclusive with `path`, `url`, and `fileName`; the display name comes from upload metadata. It is limited to group files, not images, voice, or other channels. Existing reference-review and tracking requirements remain in force.

`fileSha256` is required with `fileId` and must contain upload `data.sha256` (64 lowercase hexadecimal characters), preventing UUID reuse after 24-hour expiry from replacing the content behind an old reference. The send callback checks the actual hash inside the lease and rejects a mismatch.

Uploader identity supports auditing and accounting, not a second access grant. Other authenticated connections can query the original upload ID and reference fileId plus SHA-256. Actual-byte integrity, TTL, concurrency and capacity checks still apply. Retain original IDs after uncertainty; do not replay uploads or sends automatically. See the Agent interface contract for transport and channel receipts.

## API

A node credential alone permits enrollment diagnostics. An enabled authenticated Agent has the same public API and configuration access as local management.

- `POST /api/lan-agent/enrollments`: trusted management issues a single-use ticket.
- `POST /api/lan-agent/enroll`: submit `{ ticket, nodeId, enrollmentSecret }` to enroll or repair the original node credential. Connector 0.2.5 generates a 32-byte random secret encoded as 43 base64url characters and saves it privately before sending; Manager stores only its hash. An already completed request with the same node and recovery secret returns the same result after a lost response, consumed ticket or Manager restart, without rotating credentials or changing explicit disables. Other creation or repair requests still require a valid ticket. Legacy clients omitting this field support first enrollment only and cannot replace an existing node.
- `GET /api/lan-agent/self`: read the caller's own identity and connection state, not other nodes.
- `GET /api/lan-agent/capabilities`, `GET /api/lan-agent/resources`, `GET /api/lan-agent/resources/read?id=<resourceId>`: authorized Agents discover operations and read restricted resources.

- `GET /api/lan-agent/releases/manifest` and `GET /api/lan-agent/releases/<version>/node/<assetPath>`: manifest and files.
- `GET /api/lan-agent/nodes`: nodes, release information and recent tasks.
- `GET /api/lan-agent/instances`: local and remote instances with their Agents.
- `POST /api/lan-agent/instances/<instanceId>/agents`: add an Agent.
- `POST /api/lan-agent/instances/<instanceId>/agents/<agentId>/<operation>`: configure, scan, threads, hooks, context and tasks.
- `POST /api/lan-agent/nodes/<nodeId>/tasks`: delivery requires explicit `agentId`, `targetAgent`, full `threadId` and `message`, without default-target inference; deduplicate with `idempotencyKey`.
- `POST /api/lan-agent/nodes/<nodeId>/update`: update request.
- `WS /api/lan-agent/connect`: `authenticate → authenticated → hello → connected → heartbeat`.

The existing `lan-agent` connection and release API paths remain available for installed connectors to update. The unreleased `lanAgent` provider and `lanAgentNodeId` setting have been removed; routes use instance bindings and the user-facing feature is Remote Agent. Old Remote Agent v3 is a separate experimental protocol, not a delivery path or installation dependency of this adapter. Migrating it is outside this change.

## Route targets and delivery-test contract

`agentAdapters` stores local provider types; `remoteAgentTargets` stores `{ id, provider, instanceId, agentId }`. The remote key is `remote:<URI-encoded instanceId>:<URI-encoded agentId>`; a local key is `local:<provider>`. `primaryAgentTarget` selects the full target key, with an empty string indicating no selection. `primaryAgentAdapter` is only a derived provider and cannot distinguish computers. Remote workspace, session, and model settings remain owned by the instance.

Existing managed Route saves persist these fields. PATCH/POST `/api/rabi/instances/:guid/routes/:routeId/agent-binding` also accepts `remoteAgentTargets` and `primaryAgentTarget`, retaining its existing administrator authorization, configuration-version, and idempotency contract. The legacy `agentAdapter` parameter explicitly selects a local target without removing other targets.

`POST /gateways/:id/agent-delivery-test` performs **real delivery**, not a preview. Its body may specify `agentTargetId`; an accompanying `agentAdapterType` must match that target. A legacy provider-only request selects local; omitting both uses the saved primary. Successful responses include `data.agentTargetId` alongside the existing result. Missing, mismatched, or offline targets fail without substitution. After an uncertain result, inspect the original task before any retry. The request reuses connection authentication and checks Route enablement and the delivery contract.

Local `POST /api/agent/threads` operations may explicitly provide `agentTargetId: "local:<agentAdapter>"`. It must match `agentAdapter` and cannot accompany a remote `instanceBinding`. This disables remote-owner inference from a colliding session ID. Remote operations retain explicit instance bindings or instance paths. Legacy callers without the marker retain their existing resolution contract; authentication and task permissions remain unchanged.

Secretary sessions and bindings persist `agentTargetId`, isolating identical session IDs on different computers. Legacy ownership is attributed only during legacy configuration migration; a record missing target identity in an already migrated configuration is not automatically assigned to a subsequently selected primary.

## Capability boundary

The implementation unifies instance identity, catalogs, Agent management and remote transport. Instances link to their bound routes' shared complete settings. Advanced task dispatch, state isolation and Hook ownership have implementation and local contract coverage; plan responses, the message-processing board and full workflows still require acceptance with real remote hosts. A connected node or passing local fixture does not prove two-computer or complete advanced-feature parity.
