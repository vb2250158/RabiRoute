# 操作、ログ、トラブルシューティング

「返信がない」ということを、分割できない問題として扱わないでください。メッセージ パスをたどって、中断がプラットフォーム、ルール、ハンドラー配信、または出力段階のいずれであるかを特定します。

```text
Message adapter -> event record -> rule match -> AgentPacket -> handler -> Outbox / platform
```

## Adapter scans and shared storage

メッセージアダプタスキャンは、マネージャHTTPスレッド上の共有メッセージファイルを読み取る代わりに、履歴証拠としてバックグラウンド診断スナップショットを使用する。スナップショットがウォームアップしている間、または読み取りが失敗している間、履歴は未確認のままになります。後でリフレッシュしてください。履歴記録は現在のログインを確認するものではありません。共有ストレージが遅いとホストのヘルスチェックがブロックされないようにする必要があります。

## Start with Diagnosis Summary

開く **ログ診断**. **診断概要** 既知の接続と構成の中断を最初に配置します。

`Path healthy` は、既知の破損が検出されなかったことを意味するだけです。それでも配信が失敗する場合は、接続の詳細と最近のログを確認してください。

![Log diagnostics showing the diagnosis summary before runtime, message-input, and handler states](../../assets/screenshots/webgui-diagnostics-en.png)

ドキュメントサンプルは実行されておらず、実際のデスクトップタスクにバインドされていないため、そのカードには明確に示されています。 **無効** そして **束縛されていない**。以下の接続の詳細と最近のログに移動する前に、このような目に見える中断を修正してください。

## 証拠をもとに破損箇所を特定する

|証拠 |意味 |次のチェック |
| --- | --- | --- |
|メッセージ記録がありません |イベントはRabiRouteに入りませんでした |プラットフォームのログイン、接続、ポート、入力ポリシー |
|メッセージ記録、いいえ `agent-packets.jsonl` |入力は機能しましたが、ルールが一致しませんでした。ペルソナ、 `configName`、ルートの種類、正規表現 |
| AgentPacket は存在​​しますが、デスクトップ メッセージはありません |ハンドラーの配信に失敗しました |タスク ID、ワークスペース、デスクトップ IPC、最後のエラー |
|デスクトップの結果、プラットフォームの応答なし |出力が完了しませんでした |返信コンテキスト、パイプライン、出力ポリシー、送信トレイ ログ |
|送信ボックスは `blocked` |ポリシーまたはターゲットの拒否された出力 |ターゲットまたは権限を修正します。ゲートを迂回しないでください。
|送信ボックスは `failed` |プラットフォーム送信が試行されましたが失敗しました。プラットフォームの状態を修復してから、明示的に再試行してください。

共通のランタイムファイルは以下に存在します `data/route/<configName>/`。ランタイム JSONL、実際のメッセージ、またはアカウント データをコミットしないでください。

## マニュアルトリガーエフェクト

**手動トリガー** を実行できます `manual_trigger` または `heartbeat` ルールは、ルールからハンドラーへのパスを検証します。

それは以下のことを行う:

- 手動トリガーおよびルーティングログを書き込む。
- 実際のAgentPacketを構築する。
- 実際のハンドラ配信を実行する。
- 実行中にターゲットタスク自体の権限を使用する。

これは、外部QQイベントをシミュレートするものではなく、副作用のないプレビューではない。制御された実際のメッセージまたは RouteDecision 証拠を使用してグループ正規表現を検証します。

## 最近のログを読む

**最近のログ** は、現在のルートの最新のゲートウェイ出力を示します。最新の時間境界とその実行における最初のエラーを見つけます。過去の起動エラーに誤解されないようにしてください。


更新後は正式な適用結果、現在の Manager の世代またはコードリビジョン、対象機能の動作を確認します。ビルド完了や `dist/` の時刻だけでは、実行中の更新を確認できません。履歴ログと現在の診断を区別してください。

## データ突然変異ログ

マネージャおよびゲートウェイは、構成、計画、メモリ、メッセージ記録、配送受領書、アイデンティティ、音声、健康記録、添付ファイル、および実行時状態の突然変異を、 `logs/manager/manager-operations-YYYY-MM-DD.jsonl`。すべてのレコードには以下が含まれます `group`, `owner`, `action`, `target`, `dataSource`、および `outcome`。 1 つの HTTP リクエストのレコードにも次の情報が含まれます。 `traceId` そして `requestId`のように、開始、コミット、拒否、および失敗したステージを相互に関連付けることができます。変更レコードには、メッセージ本文、資格情報、正常性測定値、メディア コンテンツではなく、ビジネス ID、フィールド名、ダイジェスト、カウント、結果が含まれます。

`GET /meta` を公開します `operationalLog` 付き `healthy` または `degraded`、保留中のレコード数、および最新の永続エラー。失敗したバッチはメモリ内に残り、Manager の健全性が低下を報告している間、バックオフで再試行されます。ログの永続化によってビジネスの突然変異の結果が変わることはありません。

デフォルトの保存期間は 30 日で、履歴シャード全体で 512 MiB の上限があります。オペレーターは起動環境でこれを変更できます。

- `RABIROUTE_OPERATION_LOG_RETENTION_DAYS`:保存期間(日数)。
- `RABIROUTE_OPERATION_LOG_MAX_BYTES`: 履歴ログシャードの合計バイトキャップ。
- `RABIROUTE_OPERATION_LOG_GROUPS`: comma-separated group allowlist.
- `RABIROUTE_DIAGNOSTIC_LOG_GROUPS`:選択されたグループのコールスタックを追加します。発信者を検索するときに短時間有効にします。

## NapCat が未承認または空のトークンログインで開きます

いつ **NapCat を開く** がルートからクリックされると、RabiRoute がトークンを含むウィンドウを開きます。 `/web_login` 直接URL。これにより、古いタブに残された資格情報が生成され続けるのではなく、新しい WebUI セッションが作成されます。 `Unauthorized` after a NapCat restart.

トークンフィールドがまだ空の場合は、古い NapCat タブを閉じて、 **NapCat を開く** を現在の QQ インスタンス カードから再度取得します。インスタンスに WebUI アクセス トークンが保存されていることを確認します。ソース コードがアップグレードされたにもかかわらず古い URL が開いたままの場合は、正式な更新手順でコードを適用し、現在の Manager と対象 URL を再確認します。高速スタートアップ パスは、すべての Windows プロセスを同期的に列挙することなく、OneBot と WebUI の準備状況をチェックします。完全なプロセス リストは、明示的なヘルス チェックと詳細を通じて引き続き利用できます。

## NapCat は接続されましたが、AgentPacket がありませんでした

新しいものを最初に確認します `group-messages.jsonl` または `private-messages.jsonl` レコード。

- レコードなし: QQ ログイン、WebSocket クライアント、ポート、および入力ポリシーを確認してください。
- レコードが存在します: ペルソナを確認してください `configName`、ルートの種類、ターゲットグループ、および正規表現。
- 転送されたメッセージには ID のみが含まれています。OneBot HTTP を確認し、 `get_forward_msg`.

## NapCat は受信しますが、送信できません

到達可能なOneBot HTTPは、QQコアが送信できることを証明するものではない。ログイン、クイック ログイン、デバイス検証、Windows 時間、および NapCat ログを確認します。

## メッセージ エンドポイント スキャンがタイムアウトになるか、部分的な可用性が報告される

`GET /api/scan/message-adapters` は厳密に読み取り専用の診断です。 Route または NapCat の開始、設定の書き込み、QR ログインのトリガー、自動修復の実行は行われません。独立したプローブは、1 つの共有期限の下で同時に開始されます。 `scan.partial=true` 少なくとも1つのプローブがタイムアウトしたか失敗したことを意味する。他のエンドポイントからの完了した結果は引き続き利用できます。

エンドポイントごとおよびインスタンスごとに状態を解釈する。 `QQ available` には OneBot の健全性が必要ですが、到達可能な WebUI からは推測できません。ログアウトされた個人 Weixin アダプターは、個人 Weixin にのみ影響します。ビジネス健全性検査では、単一のエンドポイント エラーが次のように要約されます。 `degraded`;システムレベルのマネージャー、ルート、またはエージェントの配信エラーのみがパトロール全体を実行します `error`。ビジネス状態を報告しますが、アプリケーションのライフサイクルを所有しません。

失敗した送信トレイの試行には、 `failed` およびドラフトデータ。一般的な自動再試行キューはありません。ログインを修復してから、重複を避けるために意図的に再試行してください。

## Codexは何も受信しません

順番にチェックしてください:

1. デスクトップが開いており、ターゲットタスクに入ることができる。
2. エージェントスキャンは、そのタスクおよびワークスペースを確認する。
3. 保存されたタスクIDは存在し、要求されたワークスペースはまだ許可されています。
4. ログ診断レポート `desktop-ipc`.
5. A `no-client-found` ウェイクアンドリトライは依然として失敗する。

固定ポート4510は使用しないでください。 `CODEX_APP_SERVER_WS_URL`、または実際の配信用の別の標準入出力ランタイム。これらは現在のトランスポートではありません。

## RabiRoute デスクトップ UI がありません

のみ `RabiRouteHost.exe` Windowsパッケージ内にManagerとDesktopを作成する。 [スタート] メニューから RabiRoute を再度開くか、実行します。 `RabiRouteHost.exe` インストールディレクトリから。 2 回目の起動では、アクティブ化リクエストが現在のホストに送信され、トレイが直接起動されることはありません。

正確な生成状態を問い合わせる:

```powershell
& "$env:LOCALAPPDATA\Programs\RabiRoute\RabiRouteHost.exe" --command status --json
```

`state=running` には次の内容を含める必要があります `applicationGenerationId`, `managerInstanceId`, `managerBaseUrl`、およびマネージャーPID。開ける `managerBaseUrl/meta` を選択し、世代、インスタンス、URL を比較します。ホストは正確な Manager READY 検証後にのみ Desktop を起動し、ホスト自身の場合は Desktop が終了します。 `/meta` 検証が一致しなくなったため、ホストは世代全体を再構築できます。

ホストが再起動回路を開いた場合、またはデスクトップがまだ存在しない場合は、検査してください `%LOCALAPPDATA%\RabiRoute\diagnostics\host\host-YYYYMMDD.log` および最新のデスクトップ証拠バンドル。走らないでください `main.py` 単独で、ポートをスキャンし、トレイをループ起動し、または廃止されたライフサイクルエントリを復元する。

ページがナビゲーション後12秒以内にロードされない場合、RibiWebGUIはページのロードに失敗したことを示す。このページを再試行すると、アクセス パラメータが保持された状態で同じパスが開きます。古いページ アセットの場合、UI は最初に 1 回自動的にリロードされます。ページが復元されない場合は、ボタンを使用してください。

## マネージャーの URL が変更されたか、ポートが占有されています

RabiRouteには、固定されたマネージャポート依存関係がない。すべての Manager 世代はオペレーティング システムに使用可能なポートを要求するため、使い慣れたポートを占有している別のアプリケーションが起動をブロックしたり、そのポート所有者の終了を許可したりすることはありません。

再起動後、古いブックマーク、コマンドライン、またはブラウザタブがまだ前の世代を指している可能性がある。この世代の作品を読む `managerBaseUrl` ホストから `status --json`、またはトレイから WebGUI を再度開きます。古いポートが応答するかどうかから現在のインスタンスの所有権を推測しないでください。ホストは、ポートの所有権ではなく、アプリケーション生成、マネージャー インスタンス、および PID を通じて READY をバインドします。

リカバリ後、ローカルまたは LAN であることを個別に確認します。 `/meta` が応答します。リレーは後でオンラインになることができます、リモート `/api/events` そして `/api/speech/events` 再接続してもメディア範囲リクエストが返されます `206`。 Relay がオフラインの間も、Manager を繰り返し再起動しなくても、ローカルおよび LAN アクセスは利用可能な状態を維持する必要があります。

リモート WebGUI が選択された PC Manager に到達できない場合、API 呼び出し元は構造化されたメッセージを受け取ります。 `RABI_PC_WEBGUI_UNAVAILABLE`;返答期限が戻ってくる `RABI_PC_WEBGUI_TIMEOUT`。どちらも含まれます `retryable`, `Retry-After`、および診断要求ID。ブラウザのナビゲーションには、空白またはサイレントの 502 ではなく、同じ ID が表示されます。その ID をリレー ログと関連付けて、PC を確認します。 `/meta` エンドポイントおよびマネージャのログ。 502 を成功として扱ったり、やみくもに書き込みリクエストを繰り返したりしないでください。

計画承認の提出がマネージャーの再起動または一時的なネットワーク中断と同時に発生した場合、ページは接続の問題を明示的に報告し、フィードバック テキスト、添付ファイル、および同じ冪等を保存します。 `feedbackId`。ヘッダーが表示されるまで待ちます `Manager connected` または `/meta` が応答したら、直接再試行します。古いビルドでは生のブラウザ エラーが表示されるため、フィードバックを再入力したり、別の承認エントリを作成したりしないでください。 `Failed to fetch`.

## ペルソナ コンテンツは利用できません

ペルソナ設定が表示される場合 `Persona file is unavailable.`では、まず選択したファイルが読み取り可能であることを確認します。スピーチ ページにペルソナがリストされているが、ルート ペルソナ セレクターが空の場合、古いバージョンでは診断ワーカーの入力からペルソナ カタログ スナップショットが省略されている可能性があります。修正バージョンに更新し、トレイから WebGUI を再度開き、コンテンツとアバターを確認します。ペルソナファイルを再作成する必要はありません。診断ワーカーは、ページ要求中に共有ストレージを再スキャンせずに、コミットされた同じペルソナ スナップショットを使用します。

## プランステータスのロードに失敗します

`PLAN_STATUS_CONFIG_INVALID` ペルソナ設定の欠落ではなく、スタートアップ移行のブロックを示す可能性があります。ペルソナを確認する `legacyAliases` そして `/meta` `planStorageStartup`;エイリアスは存在するが移行が失敗した場合は、ローカルの Manager ログで具体的な原因を調べてください。古いバージョンでも受信可能 `EPERM` NAS上の古いプランロックを置き換えるときに、履歴のバックフィルとその後のステータス変換を防止する。固定リカバリでは、古いロックが再利用フェンスの下に保存され、空の名前と排他的パブリケーションが使用されます。更新または競合により乗っ取りが中止され、回復の証拠が保存されます。

更新する前に関連する計画データをバックアップし、完全なホストが所有するマネージャにリカバリを実行させる。待ってください `planStorageStartup.state=ready`、次に、現在の計画リストとアーカイブされた計画リストを確認します。移行の失敗を隠すために、プランを空にしたり、ロック ディレクトリを削除したり、ステータスを直接書き換えたりしないでください。

## いつ再起動するか

次の場合に再起動します。

- 更新の対応表で Host によるライフサイクル切り替えが必要とされている場合。対応するホットパッチは元の公開入口から適用します。
- 接続設定の適用に再起動が必要と明示されている場合。Manager の URL が変わっただけなら、動的発見をやり直します。
- 対象 Route の復旧手順が、その Route の再起動を要求している場合。独立した正常な機能は継続します。
- ログは、古いビルドがまだ実行中であることを証明します。

まず、ルール、ペルソナ、およびフォームの変更を保存します。再起動は保存ではなく、証拠もなく外部プラットフォームで再起動を繰り返すと、実際の中断が隠蔽されます。

## 有用なレポートを作成する

収集のみ:

- RabiRouteのバージョンと起動方法。
- オペレーティングシステムとNode.jsのバージョン。
- ルート メッセージ アダプターとハンドラー。
- 再現手順と期待される結果。
- 現在の起動後の最小限のログ。
- サニタイズされたステータスのスクリーンショット。
