# 一计划一会话任务持续追踪

## 适用范围

所有计划都使用本 Skill，不限于 Bug 或问题处理。例如：

- 旅游规划、活动安排、采购比较和学习计划。
- 产品设计、程序开发、内容写作和资料调研。
- Bug 调查、QA 验证、运维排障和长期跟进。

只要创建了一个计划，就必须为它定位或创建一个正式会话任务。计划的来源、领域、持续时间和最终产物不同，不改变绑定规则。

本 Skill 只管理“计划 ↔ 会话任务 ↔ 记忆”的长期追踪关系，不负责消息认领、群聊等待时间、具体审批人、领域方法、实施权限或外部发送。调用方应另外叠加对应的业务 Skill。

## 核心不变量

- 每一个计划绑定一个正式会话任务；一个正式会话任务不同时承载多个独立计划。
- 每一个计划按执行顺序保存完整 `steps`；同一时间最多一条步骤为 `进行中`，并由顶层 `currentStepId` 指向它。顶层计划为 `暂停` 时允许保留这条步骤和 `currentStepId` 作为恢复位置。
- 等待对象写入当前步骤的 `waitingFor`。先由领域 Skill 判定当前动作是否真的需要审批；确实需要审批、方案确认或授权时，补齐当前步骤的结构化 `approvalRequest` 并把 `responseStatus` 设为 `pending`。Manager 只在合同完整可提交时自动派生阻塞；`isBlocked` 是兼容投影，Agent 不得手写。
- 待 QA、待资料、待外部产物、执行失败和普通负责人等待都保持 `进行中`。计划管理者必须选择并执行询问、追问、重试、改道、拆分、升级、替代方案或补证据中的下一动作；如果确实需要用户决定暂停、取消、缩小范围或接受风险，就把该决定写成可审批合同，而不是制造不可审批的阻塞。
- 当前步骤经领域 Skill 确认需要审批、方案确认或授权时，步骤目标应直接写成“询问/追问对应负责人并取得明确结果”。合同完整后 Manager 自动阻塞实施，但计划管理者仍在每次巡检追问回执；等待资料、目标产物身份或 owner 回执不应仅因文字中出现“确认”就伪装成审批。确认命中默认授权时，必须同轮清除旧审批阻塞并续投原绑定任务。
- 同一计划从规划、调查、确认、执行到验收始终续接原会话任务，不因阶段变化重复创建。
- 计划拆成可独立管理和验收的子计划时，每个子计划各自绑定会话任务，并记录父子关系。
- 计划是状态真源；会话任务保存完整思考与执行上下文；记忆保存恢复线索、用户修正和可复用结论。
- 计划未进入终态、未暂停且没有 Manager 派生的审批阻塞时，绑定任务必须处于 `starting/active/in-progress`；禁止让可推进计划长期停在 `idle`、已结束 turn 或无人续接状态。
- 编译失败、测试失败、Unity/MCP 超时、同步未完成、尚未进包或普通负责人等待都不是阻塞；秘书必须继续选择可验证的推进动作。只有完整、可提交且 `responseStatus=pending` 的审批合同会停止合同外实施续投。
- 不按计划逐个串行等待。每次巡检都要让所有可推进计划的任务开始或继续运行，并对每个 `waitingFor` 执行一次真实询问或追问，再处理汇总。
- 控制面并发以 `planId` 为隔离键：同一计划同时只有一个管理 writer，不同计划可以并行。共享账本必须锁内合并目标记录并原子替换；全局审计只观察活动计划，不能把一个计划的未完成循环变成其它计划的队头阻塞。
- 创建任务、发送一次续接消息或得到一次回复都不等于完成；只有计划进入终态才停止追踪，进入 `暂停` 只停止继续驱动任务并保留恢复检查。
- 不得用“等待授权”“未经批准不会修改”“提交本身不会推进计划”等通用安全说明代替可判断的审批请求。
- 请求人工审批前，必须把结构化 `approvalRequest` 写入当前步骤。缺任一必要栏目时显示“审批资料不完整/禁止审批”，计划仍保持进行中，由 Agent 继续调查和补齐；合同完整且 `responseStatus=pending` 后 Manager 才自动派生审批阻塞。用户仍可通过 WebGUI 或普通消息要求补齐，Agent 必须消费反馈并更新同一计划。
- 待审批计划已经产出效果图、演示视频、设计稿、报告、补丁或其它可查看文件时，必须把实际文件作为计划顶层 `attachments` 一并写入；本机文件使用 `path`，内存内容使用 `name/mimeType/contentBase64`。不能只在 `approvalRequest.files`、标题或说明里写一个路径，导致用户看不到产物。
- Agent 不得把模糊批准解释为任意扩大权限。文件、命令、配置、数据或外部目标发生明显变化时，应更新说明并主动告诉用户，必要时再次确认。

## 审批执行合同

当前步骤需要人工审批、QA 验收、发布确认或外部写入授权时，`approvalRequest` 必须包含：

- `request`：用户这次究竟批准什么，使用可以直接回答“批准/不批准”的具体句子。
- `reason`：为什么必须在此处由人决定，不能只重复“需要审批”。
- `files`：逐项写真实路径、`create/modify/delete/move` 动作和具体改动；移动还要写目标路径。
- `commands`：逐项写将执行的完整命令、用途和预期副作用。不能只写“运行测试”“执行发布脚本”。
- `changes`：逐项写配置、数据库、云环境、外部系统或玩家数据的真实目标、变动和影响。
- `validation`：批准后如何验证成功，列出可执行检查和通过标准。
- `rollback`：失败时如何恢复；确实不适用时也要明确写出原因和失败处理方式。
- `outOfScope`：明确不会修改、不会运行、不会提交、不会发布或不会触碰的内容。

`files`、`commands`、`changes` 至少应有一类具体内容；`request`、`reason`、`validation`、`rollback`、`outOfScope` 应尽量明确。路径、命令和目标必须来自当前会话中的真实只读调查，不能猜测。尚不确定时继续调查，并把待确认内容和用户意见一起记录；用户已经给出审批意见时，先尊重并记录该意见，再由 Agent 补齐可执行说明。

`approvalRequest.files` 描述批准后将创建、修改、删除或移动什么，不等于可预览附件。需要让用户查看的现有产物必须另外写入计划顶层 `attachments`；RibiWebGUI 会在待审批卡片中以统一固定宽度的 16:9 卡片显示图片、视频和 Markdown 简短预览，并显示其它普通文件信息，点击后可打开对应的页内完整预览。视频播放标识和时长由 WebGUI 读取媒体 metadata 后自动显示，Agent 只需提交真实视频附件，不要猜测或伪造时长字段；Markdown 同样只需提交真实 `.md` 文件，由 WebGUI 自动生成简短预览，不要把完整正文重复塞进计划描述。

收到批准后，只执行用户意见和现有说明中能够明确理解的范围，不根据空白字段自行扩权。执行中发现需要新增文件、命令、外部写入、删除、发布或明显扩大范围时，更新 `approvalRequest` 并告知用户；是否再次确认按实际风险判断，不制造机械门禁。Agent 应记录审批意见，但仍需单独 PATCH 计划推进步骤；审批记录本身不自动改变计划状态。

收到审批建议、追问或纠正时，处理顺序固定为：先读取当前计划与反馈，按意见 PATCH 更新计划、步骤和必要的 `approvalRequest`，再把面向用户的处理说明以 `author=agent`、`kind=approval_response` 回写同一 `planId` / `stepId`。回复正文以计划审批记录为交付位置；Agent 会话里的最终文本只保留简短处理状态，不重复输出正文。

## 建立或恢复绑定

1. 读取计划，确认 `planId`、标题、目标、范围、预期产物、验收标准、全部 `steps`、`currentStepId`、当前状态和下一步。
2. 用目标、领域、产物、关键对象和计划标题搜索已有会话任务，不能只搜索“问题”或报错。
3. 阅读候选任务从初始需求到最新输出的完整历史，不能只看标题、摘要或最后一条消息。
4. 目标、范围和验收标准一致时复用原任务；只是关键词相似时不得错误合并。
5. 没有对应任务才创建，并在初始提示中写入完整计划、相关旧任务结论、权限边界和期望产物。
6. 保存稳定映射：`planId`、`threadId`、任务标题、计划状态、任务真实状态、最近检查时间和必要恢复索引。
7. 发现已有计划尚未绑定任务时，先补齐绑定并读取上下文，再继续推进计划。

例如，“规划一次五天旅行”是一个计划，应绑定一个任务持续保存目的地比较、预算、同行人偏好、行程版本和待确认事项；后续修改日期或酒店仍续接原任务。

## 每轮追踪循环

处理任何计划前：

1. 读取完整计划正文和当前状态。
2. 读取绑定任务从初始需求到最新输出的完整历史及真实运行状态。
3. 读取该计划绑定的记忆和映射记录；无法确认对应关系时停止推进并先修复映射。
4. 核对上轮 `nextAction`、等待对象、最新用户输入和外部事实是否仍然有效。

根据任务状态处理：

- 计划顶层为 `暂停`：不继续投递或驱动绑定任务，保留当前步骤、`currentStepId`、恢复条件和最近任务状态；用户要求恢复后先 PATCH 顶层状态为 `进行中`，再续接原任务。
- `active/in-progress`：不重复投递，只记录观察点和下次检查时间。
- `idle`：计划未终态、未暂停且没有 Manager 派生的审批阻塞时，立即从最新输出确定一个可验证的下一步并续接原任务；存在 `waitingFor` 时，必须询问、重试、改道或补证据，不能留到未知的以后。
- `failed/systemError`：优先修复并续接原任务。确认原任务不可恢复时，才建立替代任务，并记录旧 `threadId`、新 `threadId`、迁移原因和完整上下文移交。
- 已产出阶段结果：消费结果并推进计划，不反复要求同一调查、比较或产物。
- 等待普通确认、QA、资料或外部条件：每轮主动询问、追问、重试、改道或补证据，并记录真实结果；这些事项保持进行中。
- 经领域 Skill 确认需要等待审批、方案确认或授权：补齐完整 `approvalRequest` 并设 `responseStatus=pending`；Manager 自动派生阻塞。每轮复核新输入并询问或提醒负责人，禁止越过门禁实施。命中默认授权或收到批准、否决、调整、取消时，同轮更新回执并推进原绑定任务。

每轮结束前：

1. 更新计划的真实状态、全部 `steps`、唯一 `currentStepId`、`currentStep` 进展说明、`nextAction`、`waitingFor`、必要的 `approvalRequest`、阶段产物和验收结果；不要手写 `isBlocked`。完成当前步骤时先标记它为 `已完成`，再把下一条步骤切为 `进行中`。
2. 更新同一条绑定记忆，保存本轮新增事实、排除项、用户修正、关键决定和下一恢复点；没有新结论时也记录本轮核对范围和恢复点，不新建同义记忆。
3. 更新映射记录中的任务真实状态、最近检查时间、下一检查时间和本轮结果。
4. 回读计划、记忆和映射，确认写入成功后才结束本轮。

## 全计划效率巡检

每次 heartbeat、恢复运行或完成一个任务回合后：

1. 枚举全部未进入终态的计划，不能只检查最近命中或当前打开的计划；暂停计划只核对是否收到恢复指令，不进入可推进队列。
2. 逐项读取绑定任务的真实状态。标题、账本状态和“已投递”日志不能代替正式任务状态。
3. 保持 `active/in-progress` 任务运行，不重复打断。
4. 对所有 `idle/failed/systemError`、非暂停且没有 Manager 派生审批阻塞的任务，在本轮立即续接唯一下一步；不要等另一个计划完成后再启动。
5. 对每个仍有 `waitingFor` 且没有 Manager 派生审批阻塞的当前步骤，本轮必须执行一次询问、重试、改道或补证据动作，并记录渠道、回执和结果；同一次巡检不得对同一计划重复发送。
6. 任务已完成一个 turn 但计划未完成时，消费输出、更新计划并立即启动下一阶段。
7. 巡检结束前校验：`可推进但空闲的计划数 = 0`，且所有等待项都有本轮询问动作或明确发送失败证据。不满足时本轮巡检不算完成。

如果处理端存在并发、配额或权限限制，先重试、排队、换工具、拆分或升级；真正需要负责人决定暂停、缩小范围、接受风险或采用替代方案时，把该决定登记为完整审批合同，不能静默降低为“以后再做”。

## 收到业务任务完成提醒

计划绑定的独立业务任务完成一个 turn 并由 Stop Hook 回传阶段结果时，主人格必须在同一轮组织计划管理秘书闭环，不能只总结、转述或回复“已收到”：

1. 读取提醒对应的完整计划、记忆、当前步骤以及绑定任务真实状态，消费已经完成的结果，避免重复安排同一工作。
2. PATCH 更新计划步骤、顶层状态、`currentStepId`、`nextAction`、`waitingFor`、必要的 `approvalRequest` 和同一条恢复记忆；不要手写 `isBlocked`。
3. 计划未终态、未暂停且没有真实阻塞时，立即通过 `/api/agent/threads` 的 `action=send`，向该计划自身 `taskBinding.sessionId + workspace` 精确续投一个可验证的下一步；Agent 互投还要填写发送任务自己的 `sourceThreadId` 和职责对应的 `sourceAgentType`，由 Manager 核对并显示真实来源；不能按“协助处理计划1/2”的名称猜测，也不能等下一次 heartbeat。
4. 计划暂停或计划管理秘书轮转时保留业务 `taskBinding`；只有业务任务确实失效并完成受控迁移时才改绑。计划完成后也可以保留绑定作为历史证据。
5. 多条计划可以独立推进时，使用全部可用秘书槽并行管理不同分片；同一 `planId` 仍只允许一个秘书写。秘书只负责计划、记忆、任务查重、状态核对、结果消费和续投；不得做业务调查、实现、测试或修改业务文件。
6. 秘书可以创建临时子 Agent 加速计划盘点、任务查重、状态核对和结果摘要，但秘书及其子 Agent都不是业务 owner。实际工作始终由计划 `taskBinding` 指向的独立业务任务负责。
7. 本轮结束前再次读取全部计划与绑定任务，确认 `可推进但无人管理的计划数 = 0`，且 `可推进但空闲的业务任务数 = 0`。`active/in-progress` 业务任务保持运行，不重复投递。

经领域 Skill 确认需要等待审批、方案确认或授权时，必须按本 Skill 补齐 `approvalRequest`；只有合同完整且 `responseStatus=pending` 时才由 Manager 派生审批阻塞。合同不完整以及待 QA、资料、目标产物身份、owner 回执或外部产物都继续推进，不得只按自由文本关键词派生审批。

## 等待询问与唯一阻塞门

计划只有一个阻塞门：当前步骤存在完整、可提交且 `responseStatus=pending` 的 `approvalRequest`。此时用户界面一定提供可审批入口，计划管理者继续询问、追问和记录回执，绑定业务任务停止合同外实施续投。批准、否决、要求调整或取消后，同轮更新回执状态并继续推进。

任何不满足该合同的困难都不是阻塞。首次发现普通等待、工具失败、资源缺失或外部条件未满足时，必须选择下一种可执行动作：询问负责人、重试、切换工具、改道、拆分任务、升级、使用替代产物、补证据或调整方案。没有外发权限时，向计划负责人或用户提交待发送内容和所需授权；若真正需要人决定下一步，就把“暂停 / 取消 / 缩小范围 / 接受风险 / 采用替代方案”写成具体审批请求。

负责人已给出明确结论时，立即更新计划与记忆并推进下一步。只给出时间点但没有结论时，仍在每次巡检复核并追问；收到结果前不把等待误写成阻塞。

## 状态设计

正式顶层状态固定为：

`未开始 → 进行中 → 暂停 → 已完成 → 已归档`

规划、调查、待执行、待验收等领域阶段写入 `steps`、`currentStep`、`waitingFor` 和关键词，不自行发明顶层状态。旅游规划的“产物”可以是已确认行程，调研计划的“产物”可以是报告，工程计划的“产物”可以是通过验证的改动。

## 暂停与恢复

- 只有用户、计划负责人或已有授权规则明确要求暂时停止推进时，才把顶层 `status` PATCH 为 `暂停`；普通等待和可重试故障仍保持 `进行中`。
- 暂停时保留唯一的 `进行中` 步骤与 `currentStepId`，并在 `currentStep`、`nextAction` 或来源说明中记录恢复条件。不要把步骤状态改成“暂停”。
- 暂停计划不继续驱动绑定任务，不按 `blockedBy` 派生人工审批，也不因为仍有 `approvalRequest` 就请求用户再次批准。
- 收到恢复指令后，只把顶层 `status` PATCH 回 `进行中`，回读计划确认恢复位置，再续接原会话任务。

## 终态

只有以下情况可以停止主动追踪：

- 计划产物满足验收标准并完成。
- 用户明确取消计划。
- 计划被确认无效，并记录关闭依据。
- 计划被另一个计划正式替代，且新旧映射、迁移内容和替代原因已记录。

验证或确认失败时必须回到原计划和原会话任务继续推进，不能创建重复任务。
