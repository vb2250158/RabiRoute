# Message queries: Rabi first, bypass only after failure

Use this reference for requests such as “check the group,” “read the group chat history,” or “find the latest feedback,” and for searches of group and private message history. Read-only queries do not require repeated approval; they must not turn into sending messages, replaying messages, restarting services, or changing configuration.

## Discovery and queries

1. Extract the target, topic, platform, and a few synonyms from the user's wording and attachments. Use the current task's injected context, project configuration, or known bindings to determine the `roleId`, Route, group/private conversation, and time range. In the first round of business queries, search message history and related plans and memories before following matching leads into files; loading a skill or discovering a connection should involve only the necessary preparation. When the role is known, do not list Agent sessions or inspect plugin files first to guess the interface. Ask only if a critical target remains undetermined; do not enumerate unrelated accounts or groups.
2. Prefer the host-provided managed Manager GET interface. If it already handles Host discovery and `/meta` verification on every call, do not send a separate health probe. For other access methods, obtain `managerBaseUrl`, `applicationGenerationId`, and `managerInstanceId` through `RabiRouteHost.exe --command status --json`; in source mode, use the structured READY address emitted by the current Manager; external callers may explicitly supply the current complete URL. Read `<managerBaseUrl>/meta`, require `health.live=true`, `health.requiredReady=true`, and `health.state` of `healthy` or `degraded`, and verify the generation and instance identities. The target interface determines whether its own dependencies are available. Rediscover after a generation change; do not cache old URLs, scan ports, read retired instance locks, or start or terminate Manager directly.
3. A hook's summary that “Host is not running” is not evidence from a status query in this round. Distinguish an executable not found, a status timeout, a parsing failure, a not-READY state, an authentication failure, and a connection failure. For an old address or transient failure, rediscover and make one bounded retry; do not retry indefinitely.
4. For full-text message searches, use `GET /api/roles/{roleId}/message-endpoint-history?query={keywords}&match=any&includeArchives=1&limit=10`. URL-encode path and query parameters. `query` supports spaces, ASCII commas, Chinese commas (`，`), and Chinese enumeration commas (`、`) as separators; `match=all` requires all terms to match. Add `adapter`, `target`, `conversationKey`, `from`, and `to` according to the known target. Keep outbound replies when looking for existing answers; add `kind=group` when searching only for users' original group feedback, or `kind=private` for private-message feedback. The response returns `entries`, `count`, and `coverage`. Check message times, message IDs, reply IDs, conversations, and directions; do not treat bot replies as user feedback.
5. When project facts, historical decisions, or task ownership are involved, also use `GET /api/roles/{roleId}/knowledge/search?query={keywords}&mode=keywords&limit=10` to search plans, recent memories, and consolidated memories. Run the two queries in parallel when they are independent. If keyword search finds no suitable matches, use `mode=fulltext`; add `archived=1` for historical matters when needed. Read only the necessary `detailUrl` resources. After a plan match, check its status and original `taskBinding`. Describe only the coverage actually obtained; a knowledge-index match is not a group-message match.
6. Use `GET /api/gateways` only for necessary Route diagnostics; recent summaries do not replace history searches. `GET /api/roles/{roleId}/chat-history` stores Agent final replies and likewise does not replace message-endpoint history. If the host tool rejects a diagnostic path, continue using the permitted `/api/roles/{roleId}/message-endpoint-history`; do not repeatedly try paths or scan installation packages. For 404, timeout, 503, or insufficient coverage, follow the fallback rules below. Consult the current Rabi `docs/rabi-agent-interfaces.md` only if interface fields conflict. For empty results, first check the target, archives, and time coverage; an empty result does not prove that the group has no messages.

## Controlled bypass

- Bypass only if dynamic discovery and a bounded retry still fail, the interface is unavailable, or you have verified that it cannot cover the required history. A successful, complete empty result does not trigger connection-failure fallback; an insufficient summary window is a capability limitation. Do not bypass an authentication denial to evade permissions; independent local reads must already be authorized and have the necessary access permissions.
- When Rabi is available, locate NapCat from current Route bindings and status. When Rabi is unavailable, use only a connection explicitly provided by the current task, the current running instance's configuration, or a confirmed official log location. The existence of a configuration file does not prove that the instance is online.
- Do not select an account from old tasks, memories, installation remnants, or example ports; do not try historical accounts one by one. Before direct access, use `get_status` and `get_login_info` through the current configuration to verify online status and account identity, then query the specified target with the read-only `get_group_msg_history` and `get_msg`. Use credentials only in requests; never echo them. Stop querying that connection if the identity does not match.
- Read local logs only for the target Route/persona, group/private conversation, and time range. Check message times and coverage; do not describe old archives as live records. If no trustworthy current source is available, report the specific gap rather than guessing an address.
- Retain the source, target, message IDs, times, and coverage in the result. When bypassing Rabi, briefly explain its failure or capability limitation and identify the actual source. Distinguish “connection failed,” “zero results returned,” and “history not covered.” Start the next independent query with Rabi again; do not make the bypass the default entry point.
